암호 체계 실패

OWASP Top 10:2025 전체 위험을 먼저 살펴보고, A04 암호 체계 실패를 통해 비밀번호 저장부터 HTTPS, 키 관리와 보안 난수까지 데이터 보호의 기본 원리를 정리한다.

핵심 요약

  • 인코딩은 표시 방법을 바꾸고, 암호화는 열쇠로 내용을 숨기며, 해시는 데이터의 지문을 만든다.
  • Base64는 인코딩이고 SHA-256은 해시다. 둘 다 그 자체로 비밀번호를 안전하게 보관하는 방법은 아니다.
  • HTTPS는 브라우저와 서버가 주고받는 내용을 보호하지만, 서버에 저장된 데이터까지 보호하지는 않는다.

MISSION / OWASP TOP 10:2025

OWASP Top 10의 열 가지 위험을 이해하고, 그중 A04 암호 체계 실패를 공식 자료 다섯 개 이상으로 조사해 처음 접하는 사람도 이해할 수 있는 언어로 정리한다. 세부 권고는 2026년 11월 18일 기준으로 확인했다.

보안에서 암호화라는 말을 자주 듣는다. 개인정보를 암호화하고 HTTPS를 적용하면 중요한 정보가 모두 안전해질 것처럼 느껴진다. 나도 처음에는 OWASP의 암호 체계 실패를 단순히 암호화를 적용하지 않은 문제라고 생각했다.

하지만 암호화했는지만큼 어떤 방식으로 했는지, 열쇠를 어디에 보관했는지, 비밀번호를 어떻게 저장했는지, 안전한 난수를 사용했는지가 중요하다. 아무리 튼튼한 금고를 사용해도 열쇠를 금고 옆에 붙여 두면 소용이 없다.

ONE-LINE MODEL

암호 체계 실패는 자물쇠가 없는 문제뿐 아니라 약한 자물쇠, 노출된 열쇠와 잘못된 잠금 방법까지 포함한다.

먼저 읽는 초심자 용어 지도

키 관리 도구(KMS · HSM)암호 키를 보관하고 사용을 통제하는 전용 서비스 또는 장치다.키를 소스 코드나 데이터 옆에 두지 않도록 돕는다.
보안용 난수 생성기(CSPRNG)다음 값을 공격자가 예측하기 어렵게 만든다.암호 키와 로그인용 비밀값을 만들 때 사용한다.

OWASP Top 10:2025 한눈에 보기

OWASP는 웹사이트와 웹 서비스의 보안을 더 안전하게 만들기 위한 지식과 도구를 공개하는 비영리 보안 커뮤니티다. OWASP Top 10은 정확히 열 개의 해킹 기법을 뽑은 목록이 아니다. 웹 서비스에서 중요하게 관리해야 할 보안 문제를 열 개의 위험 범주로 묶은 인식 제고용 문서다. 2025판은 280만 개가 넘는 애플리케이션의 데이터와 보안 실무자 설문을 함께 반영하므로, 순위가 단순 발생 횟수만을 뜻하지는 않는다.

순위위험처음 접하는 사람을 위한 설명
A01접근 통제 실패권한이 없는데 다른 사람의 정보나 관리자 기능을 사용할 수 있는 문제다.
A02보안 설정 오류서버나 클라우드의 안전 기능을 잘못 설정해 공격할 틈을 열어 둔 문제다.
A03소프트웨어 공급망 실패외부 부품이나 저장소, 빌드·배포 과정이 오염되거나 제대로 관리되지 않는 문제다.
A04암호 체계 실패중요한 정보를 제대로 잠그지 않거나 약한 키·알고리즘·난수를 사용하는 문제다.
A05인젝션사용자가 입력한 글을 데이터베이스나 운영체제가 실행할 명령으로 잘못 받아들이는 문제다.
A06안전하지 않은 설계필요한 보안 규칙과 방어 장치를 설계 단계에서 빠뜨린 문제다.
A07인증 실패가짜 사용자를 진짜 사용자로 인정하거나 로그인 상태를 잘못 관리하는 문제다.
A08소프트웨어·데이터 무결성 실패코드, 업데이트와 데이터가 변조되지 않았는지 확인하지 않고 믿는 문제다.
A09보안 로깅·알림 실패공격 흔적을 남기지 않거나 기록하고도 담당자에게 제때 알리지 못하는 문제다.
A10부적절한 예외 처리오류나 장애가 발생했을 때 시스템이 안전하지 않은 상태로 동작하는 문제다.

2025판의 선정 과정과 변화는 OWASP 공식 소개에서 확인할 수 있다. 이 글에서는 그중 개인정보, 비밀번호, 로그인 상태를 증명하는 값과 통신을 직접 다루는 A04를 자세히 살펴본다.

A04 암호 체계 실패란 무엇인가

A04는 2021판의 2위에서 2025판의 4위로 내려왔다. 하지만 순위가 낮아졌다고 중요하지 않은 것은 아니다. 개인정보, 카드번호, 건강정보와 영업비밀이 노출되면 개인과 기업 모두 큰 피해를 볼 수 있다.

OWASP A04:2025는 필요한 암호화를 하지 않은 경우뿐 아니라 오래된 암호화 방식, 키 유출과 재사용, 서버 신분증인 인증서를 확인하지 않은 경우, 암호화의 세부 방식을 잘못 고른 경우, 약한 난수와 잘못된 오류 처리까지 이 범주에 포함한다. 특히 2025판은 공격자가 다음 값을 쉽게 예측할 수 있는 난수를 주요 문제로 언급한다.

  • 비밀번호나 개인정보를 암호화하지 않은 원래 모습으로 저장한다.
  • MD5·SHA-1 같은 오래된 해시 방식을 새 보안 설계에 계속 사용한다.
  • 암호화 키를 소스 코드나 공개 저장소에 넣는다.
  • 서버 인증서가 올바른지 확인하지 않거나 오류를 무시한다.
  • 시간이나 사용자 번호로 비밀번호 재설정 링크의 일회용 값을 만들어 공격자가 추측할 수 있다.
  • 암호화만 적용하고 데이터가 바뀌었는지는 확인하지 않는다.

기본부터: 인코딩·암호화·해시는 무엇이 다른가

세 가지 모두 데이터를 다른 모습으로 바꾸지만 바꾸는 목적이 다르다. 인코딩은 컴퓨터가 데이터를 다루기 편하게 표시 방법을 바꾸고, 암호화는 허가받지 않은 사람이 내용을 읽지 못하게 하며, 해시는 두 데이터가 같은지 비교할 수 있는 지문을 만든다. OWASP 보안 용어 지침을 기준으로 정리하면 다음과 같다.

세 질문만 기억하자

표시 방법만 바꾸면 인코딩, 열쇠로 잠그면 암호화, 원본을 비교할 지문을 만들면 해시다.

개념한 문장 뜻되돌리는 방법대표적인 사용 예
인코딩내용은 그대로 두고 표시 방법만 바꾼다.공개된 규칙만 알면 누구나 되돌릴 수 있다.Base64, 문자 깨짐 방지
암호화비밀 열쇠로 내용을 읽지 못하게 잠근다.올바른 열쇠가 있어야 되돌릴 수 있다.개인정보와 통신 내용 보호
해시데이터를 구별할 수 있는 지문을 만든다.원래 내용으로 되돌리는 기능이 없다.파일 비교, 비밀번호 확인

인코딩은 표시 방법을 바꾸는 규칙이다

인코딩은 같은 내용을 컴퓨터가 저장하거나 전달하기 편한 다른 모양으로 표현하는 일이다. 택배 물건을 정해진 규격의 상자에 옮겨 담는 것과 비슷하다. 포장 방법은 달라지지만 물건을 비밀로 숨기는 자물쇠는 생기지 않는다.

Base64는 대표적인 인코딩이다

Base64는 사진이나 파일 같은 데이터를 영문자·숫자·몇 가지 기호로 바꾸는 공개 규칙이다. 예를 들어 hello를 Base64로 바꾸면 aGVsbG8=가 된다. 처음 보면 암호처럼 보이지만 누구나 같은 규칙으로 즉시 hello로 되돌릴 수 있다. 비밀번호나 프로그램이 다른 서비스에 접속할 때 쓰는 비밀값을 Base64로 바꿔도 안전해지지 않는다.

암호화는 열쇠로 내용을 잠그는 기술이다

암호화는 읽을 수 있는 원본에 비밀 열쇠인 키를 적용해 알아보기 어려운 결과로 바꾸는 과정이다. 암호화 전의 원본을 평문, 잠긴 결과를 암호문, 올바른 키로 다시 여는 과정을 복호화라고 부른다. 인코딩과 달리 키가 없는 사람은 원래 내용을 읽기 어려워야 한다.

해시는 데이터의 지문을 만드는 기술이다

해시 함수에 데이터를 넣으면 일정한 길이의 결과가 나온다. 같은 데이터를 넣으면 같은 지문이 나오고, 글자 하나만 바뀌어도 전혀 다른 지문이 나온다. 암호화처럼 다시 여는 열쇠가 없으며, 원본을 복원하기보다 두 데이터가 같은지 비교하는 데 사용한다.

용어 비교인코딩 / 암호화 / 해시
인코딩   hello ── 공개된 규칙 ──→ aGVsbG8= ── 누구나 복원

암호화   읽을 수 있는 원본(평문) ── 비밀 키 ─→ 잠긴 결과(암호문)
                                           └─ 올바른 키로만 복호화

해시     입력값 ── 해시 함수 ───→ 데이터 지문 ── 원본 복원 기능 없음

SHA-256은 해시를 만드는 방법의 이름이다

SHA-256은 여러 해시 함수 중 하나다. 파일을 내려받은 뒤 배포자가 신뢰할 수 있는 경로로 공개한 SHA-256 값과 비교하면, 받은 파일이 배포자가 제공한 파일과 같은지 확인할 수 있다. 이름의 256은 결과의 길이를 뜻하며, 보통 0부터 9와 a부터 f까지의 문자로 이루어진 64자리 값으로 표시된다. 이 숫자를 외울 필요는 없다. 중요한 점은 SHA-256이 암호화가 아니며 복호화할 대상도 아니라는 것이다.

다만 “SHA-256으로 해시했다”는 사실만으로 모든 데이터가 안전해지는 것은 아니다. SHA-256은 계산이 매우 빨라 파일 비교에는 편리하지만, 공격자가 비밀번호 후보를 빠르게 시험하는 데도 유리하다. 그래서 비밀번호에는 일부러 계산을 느리게 만든 전용 저장 방식을 사용한다.

비밀번호는 왜 암호화하면 안 될까

서비스는 사용자의 비밀번호 원문을 다시 읽을 필요가 없다. 로그인할 때 입력한 값이 가입 당시 값과 같은지만 확인하면 된다. 복호화 가능한 형태로 저장하면 서버의 키가 유출됐을 때 모든 비밀번호가 한꺼번에 드러날 수 있다.

따라서 비밀번호는 평문이나 복호화 가능한 암호화 대신 비밀번호 전용 해싱 알고리즘으로 처리해야 한다. 이를 KDF(키 유도 함수)라고 부르기도 한다. 이름은 어렵지만 역할은 단순하다. 계정마다 다른 값인 salt를 섞고, 후보 하나를 확인할 때마다 일부러 시간과 메모리를 쓰게 해 공격자의 대량 추측을 느리게 만든다.

OWASP 비밀번호 저장 지침은 새 시스템에서 Argon2id를 우선 권고하고, 사용할 수 없다면 scrypt 같은 대안을 제시한다. 이 이름들을 모두 외울 필요는 없다. 사용하는 개발 도구가 제공하는 최신 구현을 선택하고 OWASP의 현재 권고에 맞게 설정하는 것이 중요하다.

비밀번호에 SHA-256만 한 번 적용하면 왜 부족한가

앞에서 살펴본 것처럼 SHA-256은 계산이 너무 빨라 비밀번호 저장에 단독으로 사용하기 어렵다. 비밀번호에는 후보를 확인할 때마다 시간과 메모리를 쓰는 전용 방식을 사용한다.

salt(솔트)는 숨겨야 할 비밀이 아니라 계정별 고유값이다

salt는 계정마다 새로 만들어 비밀번호와 함께 처리하는 고유값이다. 두 사람이 같은 비밀번호를 쓰더라도 서로 다른 salt를 섞으면 저장 결과가 달라진다. 공격자가 자주 쓰는 비밀번호의 결과를 미리 만들어 둔 목록을 여러 계정에 그대로 적용하기도 어려워진다.

비밀번호 저장고유값 + 계산 비용
사용자 A의 비밀번호 + 고유 salt A ─→ 전용 비밀번호 해시 ─→ 결과 A
사용자 B의 비밀번호 + 고유 salt B ─→ 전용 비밀번호 해시 ─→ 결과 B

같은 비밀번호를 입력해도 salt가 다르면 저장 결과가 달라진다.

salt는 비밀번호가 아니므로 숨길 필요가 없고 해시 결과와 함께 저장해도 된다. 핵심은 계정마다 고유하고 안전한 난수로 생성되는 것이다. 미국 표준기술연구소(NIST)가 2025년 7월 공개한 디지털 신원 지침 SP 800-63B-4도 비밀번호를 salt와 계산 비용 설정을 갖춘 적절한 방식으로 해시하도록 안내한다. 계산 비용은 비밀번호 후보 하나를 확인할 때 사용할 시간과 메모리의 양을 뜻한다. 사용한 방식과 설정도 함께 기록해야 나중에 더 강한 방식으로 바꿀 수 있다.

HTTPS와 TLS는 무엇이며 어디까지 보호할까

HTTP는 브라우저와 웹 서버가 페이지와 데이터를 주고받는 규칙이다. 여기에 보안 기능을 더한 것이 HTTPS이며, 주소창이 https://로 시작하는 사이트가 이를 사용한다. 마지막의 S는 Secure, 즉 안전하게 보호한다는 뜻이다.

HTTPS는 TLS라는 통신 보호 규칙으로 브라우저와 서버 사이에 암호화된 통로를 만든다. 카페의 공용 와이파이를 사용하더라도 중간에 있는 사람이 아이디, 비밀번호와 메시지 내용을 훔쳐보기 어렵게 한다. 또한 브라우저는 사이트의 온라인 신분증인 인증서를 확인해 접속하려던 주소의 서버가 맞는지 확인한다. 인증서는 서버의 신원을 확인하는 수단이지 그 사이트의 모든 내용이 안전하다는 보증서는 아니다.

그러나 HTTPS는 사용자와 서버 사이의 전송 구간을 보호한다. 서버가 개인정보를 평문으로 저장하거나, 사용자의 휴대전화나 컴퓨터가 이미 감염됐거나, 웹 서비스가 권한 없는 사용자에게 데이터를 보여 주는 문제까지 해결하지는 않는다. 택배 이동 중에는 튼튼한 보안 차량을 쓰더라도 출발지와 도착지의 창고까지 자동으로 안전해지는 것은 아닌 것과 같다.

HTTPS 보호 범위이동 중인 데이터
사용자 기기 ═════ HTTPS / TLS 보호 구간 ═════ 서버
    │                                         │
감염된 기기는 별도 문제                 저장 데이터와 서버 권한은 별도 문제

TLS에도 세대별 버전이 있으며 오래된 버전에는 알려진 약점이 있다. 인터넷 표준 문서 RFC 8996은 TLS 1.0과 1.1을 공식 폐기했다. 2026년의 RFC 9852는 새로 만드는 통신 규칙이 TLS 1.3을 기본으로 요구하도록 한다. TLS 1.2도 올바르게 설정하면 사용할 수 있지만, 새 서비스에서는 TLS 1.3을 우선하고 TLS 1.3을 지원하지 않는 기존 시스템과 연결해야 할 때 TLS 1.2를 추가로 고려하는 편이 적절하다.

좋은 알고리즘보다 어려운 키 관리

AES는 전 세계에서 널리 검증된 표준 암호화 방식이다. 그러나 AES를 사용했다는 사실만으로 안전이 보장되지는 않는다. 암호화 키를 프로그램 코드에 직접 적어 두면 코드 저장소나 배포 파일이 노출될 때 키도 함께 유출될 수 있다.

키 관리

암호화된 데이터와 복호화 키를 같은 위치에 두는 것은 잠긴 금고 옆에 열쇠를 붙여 두는 것과 같다.

키는 코드와 코드 저장소에서 분리해야 한다. 키 관리 서비스(KMS)는 키의 생성, 사용 권한, 교체와 사용 기록을 한곳에서 관리한다. 더 강한 보호가 필요한 곳에서는 키를 장치 밖으로 꺼내지 않은 채 내부에서 암호화·복호화 작업을 수행하는 보안 하드웨어(HSM)를 사용할 수 있다. 두 도구 모두 접근 권한을 너무 넓게 주면 안전하지 않으므로 필요한 서비스에만 최소 권한을 부여해야 한다.

프로그램을 실행할 때 외부에서 전달하는 설정값인 환경 변수에 키를 넣는 것만으로도 충분하다고 생각하기 쉽다. 그러나 실행 중인 프로그램의 정보, 오류 화면과 자동 빌드·배포 로그를 통해 노출될 수 있다. 따라서 환경 변수를 그 자체로 안전한 금고라고 생각해서는 안 된다.

NIST SP 800-57 Part 1 Rev.5는 키를 생성하는 순간부터 저장·전달·사용·교체·폐기하는 전체 과정을 관리하도록 안내한다. 유출이 의심되거나 알고리즘의 안전성이 달라졌을 때 신속히 교체할 수 있어야 하며, 어떤 데이터가 어떤 키로 보호됐는지도 추적해야 한다.

키 관리 과정사고 전에 준비하기
안전한 생성 → 제한된 배포 → 보호된 저장 → 최소 권한 사용
       → 사용 기록·감사 → 교체·취소 → 안전한 폐기

암호화했는데도 데이터가 바뀔 수 있다

암호화의 기본 목적은 허가받지 않은 사람이 내용을 읽지 못하게 하는 기밀성이다. 사용하는 방식에 따라서는 공격자가 내용을 읽지 못해도 암호문을 바꿀 수 있다. 그래서 내용을 숨기면서 변경 여부까지 함께 확인하는 인증된 암호화(AEAD)를 사용해야 한다. 여기서 인증은 사용자 로그인이 아니라 데이터가 중간에 바뀌지 않았는지 확인한다는 뜻이다. 잠긴 봉투에 위조 방지 봉인까지 붙이는 것과 비슷하다.

OWASP 암호화 저장 지침은 AES-GCM을 인증된 암호화의 한 예로 안내한다. 이런 이름을 모두 외우거나 세부 값을 개발자가 직접 조립할 필요는 없다. 검증되고 꾸준히 관리되는 라이브러리의 안전한 기능을 사용하는 편이 중요하다.

암호화할 때는 같은 내용도 매번 다른 결과가 나오도록 돕는 추가 값이 필요하다. 이를 초기값(IV)이나 일회성 값(nonce)이라고 부른다. 비밀 키와는 다르며, 필요한 조건은 암호화 방식마다 조금씩 다르다. 개발자는 선택한 라이브러리의 규칙을 따르고 같은 키에서 값을 잘못 재사용하지 않아야 한다.

확인 대상질문실패했을 때의 문제
암호화 방식현재 검증된 표준과 라이브러리를 사용하는가?이미 알려진 공격이나 구현 약점에 노출된다.
키안전하게 생성·저장하고 접근을 제한했는가?강한 암호문도 공격자가 복호화할 수 있다.
변조 확인내용을 숨기는 동시에 변경 여부도 확인하는가?공격자가 암호문을 바꿔도 알아채지 못한다.
초기값선택한 방식의 규칙대로 만들고 잘못된 재사용을 막는가?같은 키에서 반복 사용하면 암호화를 안전하다고 보기 어려워진다.
오류 처리실패 정보가 공격자에게 단서를 주지 않는가?서로 다른 오류 메시지가 비밀값을 추측할 단서가 될 수 있다.

게임용 난수와 보안용 난수는 다르다

게임 캐릭터의 행동이나 화면 요소를 섞을 때는 일반 난수 함수로 충분할 수 있다. 하지만 암호화 키, 로그인 상태를 증명하는 임시값인 세션 ID, 비밀번호 재설정 링크와 외부 서비스 호출용 비밀값은 공격자가 다음 값을 예측하기 어려워야 한다.

사용자 번호와 현재 시간을 조합해 비밀번호 재설정용 일회성 값을 만들면 다른 사용자의 값도 추측할 수 있다. 이런 값에는 일반 난수 생성기가 아닌 보안용 난수 생성기(CSPRNG)를 사용해야 한다. CSPRNG는 앞에서 나온 값을 많이 보더라도 다음 값을 예측하기 어렵게 설계된 기능이다. 개발자가 직접 만드는 대신 운영체제와 프로그래밍 언어가 제공하는 검증된 기능을 사용하는 것이 원칙이다.

난수의 용도일반용 / 보안용
일반 난수  → 화면 효과 · 게임 동작 · 무작위 순서 정하기
보안 난수  → 암호 키 · 로그인 임시값 · 재설정 링크 · 외부 서비스 비밀값

NIST SP 800-90C는 공격자가 다음 값을 예측하기 어려운 고품질 난수를 만드는 기준을 다룬다. 웹 서비스 개발자는 이 복잡한 방식을 직접 구현하기보다 운영체제와 개발 도구가 제공하는 보안용 난수 기능을 올바르게 호출하는 데 집중해야 한다.

자주 하는 오해와 예방 순서

Base64면 암호화됐다Base64는 공개된 규칙으로 되돌릴 수 있는 인코딩이다.
SHA-256이면 비밀번호도 안전하다빠른 일반 해시는 대량 추측에 유리하므로 전용 비밀번호 해시가 필요하다.
HTTPS면 서비스 전체가 안전하다TLS는 전송 구간을 보호하며 저장 데이터와 서버 권한은 별도로 보호해야 한다.
AES를 썼으니 안전하다키 보관, 변조 확인, 초기값과 오류 처리까지 올바르게 사용해야 한다.

자체 알고리즘은 구조를 몰라서 안전하다널리 검증된 표준과 유지관리되는 라이브러리를 사용해야 한다.

현실적인 예방 순서

  • 보호할 데이터를 분류한다. 개인정보, 인증정보와 결제정보가 어디에서 생성·전송·저장되는지 파악한다.
  • 불필요한 민감정보는 저장하지 않는다. 보관하지 않은 데이터는 저장소 침해 때 함께 유출되지 않는다.
  • 검증된 표준과 라이브러리를 사용한다. 자체 암호 알고리즘이나 임의로 조합한 통신 규칙을 만들지 않는다.
  • 비밀번호는 전용 방식으로 저장한다. 계정별 고유값(salt)과 환경에 맞는 계산 비용을 적용한다.
  • 현대적인 TLS를 사용한다. 인증서 검증을 생략하지 않고 TLS 1.0과 1.1을 비활성화한다.
  • 인증된 암호화를 선택한다. 저장 데이터의 기밀성과 변조 여부를 함께 보호한다.
  • 키와 비밀값은 보안용 난수 생성기로 만든다. 시간값과 일반 난수를 보안용 비밀 생성에 사용하지 않는다.
  • 키를 데이터와 코드에서 분리한다. 전용 비밀 관리 시스템과 최소 권한을 적용한다.
  • 교체와 복구를 미리 시험한다. 키 유출 뒤 처음 절차를 고민하지 않도록 생성·사용·교체·폐기 과정을 준비한다.
  • 로그를 점검한다. 비밀번호, 키, 로그인용 비밀값과 평문 개인정보가 오류 메시지에 남지 않게 한다.

정리 — 암호화는 기능이 아니라 운영 체계다

이번 조사를 통해 암호 체계 실패는 단순히 암호화를 하지 않은 문제만을 뜻하지 않는다는 점을 알게 됐다. 검증된 알고리즘도 키를 코드에 넣거나 비밀번호에 빠른 일반 해시를 사용하고, 예측 가능한 난수로 로그인용 비밀값을 만들면 보호 기능을 잃는다. HTTPS 역시 통신 구간을 보호할 뿐 시스템 전체를 자동으로 안전하게 만들지는 않는다.

중요한 것은 어려운 암호 알고리즘을 직접 만드는 일이 아니다. 무엇을 보호해야 하는지 파악하고 목적에 맞는 검증된 기술을 사용하며, 키와 비밀정보가 만들어져 폐기될 때까지의 과정을 관리해야 한다. 암호화는 보안을 완성하는 마법의 버튼이 아니라 올바르게 사용하고 계속 관리해야 하는 도구다.
