차량의 안드로이드가 해킹당해도
제어권은 지킬 수 있을까

PAPER PROFILE

Haochen Gong 외 7명, Harness: Transparent and Lightweight Protection of Vehicle Control on Untrusted Android Automotive Operating System, 34th USENIX Security Symposium, 2025, pp. 4265–4284. 공식 논문 페이지

차에서 안드로이드 화면을 본다고 하면 스마트폰 화면을 차량에 비추는 Android Auto부터 떠올리기 쉽다. 이 논문이 다루는 Android Automotive OS(AAOS)는 다르다. 운영체제가 차량의 헤드유닛에서 직접 실행되고, 공조·도어·시트 같은 차량 기능과 연결된다. 편리하지만 공격자에게는 스마트폰 앱, 브라우저, 시스템 서비스에서 차량 ECU까지 이어지는 통로가 될 수 있다.

저자들은 대담한 가정에서 출발한다. “안드로이드가 이미 뚫려 공격자가 root 권한까지 얻었다면?” 보통 운영체제가 장악되면 게임이 끝났다고 생각한다. Harness는 그 상황에서도 사용자가 실제로 누른 차량 제어만 ECU에 도달하게 하자고 제안한다. 침입 자체를 완벽히 막는 대신, 침입 이후의 피해 경계를 다시 세우는 연구다.

이 논문을 고른 이유

이 논문을 고른 이유는 AAOS와 소프트웨어 정의 차량처럼 실제 자동차 업계에서 중요해지는 기술을 다루면서도, 신뢰 경계·가상화·최소 권한이라는 보안 실무의 핵심 개념을 함께 배울 수 있기 때문이다. 공격 장면만 보여주는 데서 끝나지 않고 방어 시스템을 직접 설계한 뒤 보안성과 성능을 함께 평가했다는 점도 마음에 들었다.

공개 아티팩트가 있어 논문 요약을 넘어 분석과 재현으로 발전시킬 수 있고, 차량 보안 직무 면접에서도 “무엇을 신뢰하며, 어떤 공격까지 막고, 그 대가로 얼마의 성능을 지불하는가”를 구체적으로 설명할 수 있다는 점이 최종 선택의 이유였다.

읽기 전, 세 가지 질문

이 논문이 해결하려는 문제는 무엇인가?

AAOS의 차량 제어는 화면에 버튼을 그리는 HMI, 앱과 시스템 서비스 사이의 Binder 통신, VHAL(Vehicle Hardware Abstraction Layer), 차량 내부 네트워크를 차례로 지난다. 이 중 하나라도 조작되면 사용자가 누르지 않은 명령이 차량으로 갈 수 있다. 논문의 문제는 이 전체 제어 사슬을 침해된 운영체제로부터 어떻게 보호할 것인가이다.

왜 중요한가?

소프트웨어 정의 차량은 기능을 중앙 컴퓨터로 모으고 OTA로 계속 갱신한다. 개발 속도와 사용자 경험은 좋아지지만, 복잡한 IVI가 실제 차량 제어와 가까워진다. 음악 앱의 취약점이 공조나 도어 제어로 번지지 않도록 경계를 설계하는 일은 실무에서 말하는 defense in depth와 직접 연결된다.

기존 방식은 무엇이 부족했는가?

기존 TEE·격리 기술은 주로 하나의 앱이나 코드 조각을 보호했다. 그러나 AAOS의 차량 제어는 여러 프로세스가 공유 메모리와 Binder로 협력하고, 화면 출력과 터치 입력까지 신뢰해야 한다. 모든 프로그램을 수정하거나 별도의 보안 화면을 요구하면 폐쇄형 드라이버가 많은 차량 환경과 빠른 OTA 개발에 적용하기 어렵고, 운전자에게 확인 절차를 늘리는 것은 오히려 안전을 해칠 수 있다.

기 — 화면의 버튼에서 ECU까지

공조 버튼을 한 번 누르는 동작을 단순화하면 다음과 같다.

VEHICLE CONTROL CHAINAAOS
운전자 터치
  → 화면·입력 시스템(HMI)
  → 차량 제어 앱
  → CarService ── Binder IPC
  → VHAL
  → 차량 내부 네트워크(IVN)
  → 공조·도어 등의 ECU

저자들은 이 흐름을 HMI, 처리, 출력의 세 단계로 나누고 커널과 사용자 영역에서 가능한 13가지 공격 전략을 정리했다. 가짜 시스템 서비스를 등록하거나, Binder 요청을 위조하거나, 공유 메모리를 바꾸거나, 가짜 터치를 주입하거나, 마지막에 차량 네트워크 명령을 직접 보내는 식이다. 서로 다른 공격처럼 보여도 목적은 하나다. 제어 사슬 어딘가에서 “사용자의 의도”를 공격자의 명령으로 바꾸는 것이다.

THREAT MODEL

공격자는 AAOS의 취약점을 이용해 root 권한, 임의 메모리 접근, 코드 실행까지 얻었다. 반면 하이퍼바이저와 IOMMU, Harness가 보호하는 프로그램 자체, 초기 secure boot는 신뢰한다. 물리 공격·DoS·사이드채널·원격 제어와 AI 모델 공격은 범위 밖이다.

이 위협 모델은 논문을 정확히 이해하는 열쇠다. Harness는 안드로이드 해킹을 탐지하는 백신이 아니다. 공격자가 AAOS를 장악한 뒤에도 보호 영역의 메모리, 통신, 화면과 터치를 위조하지 못하게 하는 마지막 방어선이다.

승 — AAOS 안에 작은 신뢰 구역을 만들다

저자들은 차량 제어 앱, CarService, VHAL, HWC 등 꼭 필요한 구성요소만 최소 보호 영역으로 묶었다. SystemServer처럼 크고 외부 인터페이스가 많은 구성요소는 일부러 제외한다. 보호해야 할 코드가 커질수록 그 안에 취약점이 들어올 가능성도 커지기 때문이다. 이것이 TCB(Trusted Computing Base)를 줄인다는 말의 실제 의미다.

그 아래에는 하이퍼바이저 권한으로 동작하는 Harness Lowvisor가 있다. Lowvisor는 각 보호 프로세스를 enclave로 격리하고, 운영체제가 요청한 메모리 매핑과 Binder 통신, 입출력을 검사한다. 복잡한 스케줄링은 기존 AAOS에 맡기되, 보안에 결정적인 순간만 더 높은 권한에서 확인하는 구조다.

MINIMAL TRUST DOMAINHARNESS
[신뢰하지 않는 영역]
일반 앱 · SystemServer · AAOS 커널
             │ 요청은 맡기되 결과를 검증
─────────────┼────────────────────
[보호 영역 / process enclaves]
차량 제어 앱 · CarService · VHAL · HWC
             │
[Harness Lowvisor / Hypervisor]
메모리 격리 · Binder 보호 · HMI 검증 · ECU 암호 채널

1. 공유를 금지하지 않고, 누가 무엇을 공유하는지 기억한다

안드로이드는 성능을 위해 프로세스끼리 메모리를 많이 공유한다. 모두 막으면 시스템이 작동하지 않고, 그대로 허용하면 침해된 커널이 다른 페이지를 끼워 넣을 수 있다. Harness는 enclave가 요청한 주소·크기·권한을 기록하고, 공유 자원마다 위조하기 어려운 토큰을 붙인다. 실제 페이지가 그 의도와 일치할 때만 매핑한다.

2. Binder의 상대방과 메시지를 함께 확인한다

차량 앱과 CarService는 Binder로 대화한다. Lowvisor는 서비스 등록과 조회를 추적하고, 송신자·수신자가 같은 보호 영역에 속하는지 확인한다. 보호된 요청의 상태와 데이터를 별도 영역에 보관해 재생·변조를 막는다. 모든 메시지를 암호화하는 방식보다 Android Binder의 구조를 활용해 추가 복사를 한 번으로 줄였다.

3. 보이는 버튼과 실제 터치를 묶는다

메모리와 API만 지켜도 공격자가 화면 위에 가짜 버튼을 덮거나 터치 이벤트를 주입하면 차량을 움직일 수 있다. Harness는 HWC를 보호하고 가상 GPU·입력 장치와 결합한다. 화면에 표시된 차량 제어 GUI의 위치와 실제 터치 좌표가 맞는지 검증해, 사용자가 누른 동작만 보호 앱으로 전달한다. 별도 보안 화면이나 추가 확인 버튼은 요구하지 않는다.

전 — 보안과 성능을 함께 평가하다

연구진은 Google Cuttlefish 위의 Android 13 AAOS와 KVM을 이용해 약 9.3K LoC 규모의 프로토타입을 만들었다. 하드웨어는 Cortex-A76 4코어와 8GB RAM을 갖춘 Raspberry Pi 5였다. 보안 측면에서는 IVI 관련 공개 CVE 26개와 기존 연구의 공격 경로 3개를 분석하고, 메모리 변조·가짜 서비스·터치 주입·보호 API 호출 등의 공격을 직접 모의했다. 제시한 공격 시뮬레이션은 모두 탐지했다.

한계와 아쉬운 점

실차 검증이 아니라 프로토타입 검증이다

평가는 Raspberry Pi 5와 Cuttlefish에서 수행됐다. AOSP의 차량 API는 실제 차량 네트워크 지연을 포함하지 않고, 보드의 Cuttlefish가 GPU 가속을 지원하지 않아 그래픽 성능도 측정하지 않았다. 따라서 양산 헤드유닛에서 같은 결과가 나온다고 단정할 수 없다.

신뢰를 없앤 것이 아니라 아래로 옮겼다

AAOS는 불신하지만 하이퍼바이저, IOMMU, 초기 부팅 과정과 보호 앱의 무결성은 신뢰한다. Lowvisor나 보호 앱 자체에 취약점이 있으면 새 단일 실패 지점이 된다. 또한 논문이 제외한 DoS에서는 공격자가 차량 명령을 위조하지 못하더라도 서비스를 멈추게 할 수 있다.

“사용자의 의도”도 정의가 필요하다

올바른 GUI 위치에서 실제 터치가 들어왔다는 사실은 강한 신호다. 하지만 운전자가 속았거나 보호 앱의 로직이 잘못됐거나, enclave가 신뢰하지 않는 외부 데이터를 소비하는 경우까지 자동으로 안전해지는 것은 아니다. 논문도 외부 Android API에서 들어오는 데이터를 체계적으로 검사하는 일을 후속 과제로 남겼다.

재현 비용이 낮지는 않다

아티팩트가 공개되어 있다는 점은 장점이지만, 전체 빌드에는 x86 Ubuntu 환경과 300GB 이상의 저장공간이 권장되고 Raspberry Pi 5가 필요하다. 일부 구성요소는 협력 업체와의 비밀유지 계약 때문에 공개하지 않았다. 학부생이 첫날부터 전체 시스템을 재현하기보다 단계를 나누는 편이 현실적이다.

MY VERDICT

Harness의 가장 좋은 점은 “안드로이드를 완벽하게 만들겠다”는 약속을 하지 않는다는 것이다. 침해를 전제로 하고, 실제 피해를 일으키는 차량 제어 사슬에 최소 신뢰 경계를 다시 긋는다. 다만 아직 양산차 적용 결과가 아닌 연구용 프로토타입이라는 꼬리표를 떼어 말해서는 안 된다.

결 — 내가 배운 것은 격리 기술보다 경계 설정이었다

논문을 읽기 전에는 root 권한을 빼앗기면 모든 방어가 끝난다고 생각했다. Harness는 “무엇을 잃었고, 무엇은 아직 지킬 수 있는가”를 다시 묻는다. IVI의 풍부한 기능은 그대로 두고, 차량 제어에 필요한 최소 구성요소만 더 높은 권한에서 보호한다. 이것은 차량뿐 아니라 결제 단말, 스마트팩토리 HMI, 의료기기처럼 복잡한 운영체제가 물리 장치를 움직이는 환경에도 적용할 수 있는 사고방식이다.

실무 관점에서 특히 남은 단어는 신뢰 경계다. 어떤 컴포넌트를 TCB에 넣었는지, 왜 SystemServer는 제외했는지, 운영체제가 침해된 뒤에도 어떤 속성을 보장하는지를 설명할 수 있어야 한다. 면접에서도 “이 기술이 안전하다”보다 “무엇을 신뢰하고 어떤 공격은 막지 못한다”라고 답하는 편이 훨씬 정확하다.

앞으로 할 일 — 읽은 논문을 포트폴리오로 바꾸기

1. 이어서 공부할 것

  1. AAOS 기초: CarService, VHAL, AIDL, Binder가 버튼 입력을 차량 속성으로 전달하는 흐름을 직접 그린다.
  2. 격리 기초: VM·하이퍼바이저·TEE·enclave·TCB의 차이를 한 장으로 비교한다.
  3. 후속 논문: ReZone(USENIX Security 2022)으로 TEE의 권한 축소를, MyTEE(NDSS 2023)로 Arm 기반 격리 설계를 비교한다.
  4. 차량 네트워크 연결: A Formal Security Analysis of CAN XL(USENIX Security 2026)을 읽어 보호된 VHAL 이후의 통신까지 범위를 넓힌다.

2. 직접 해볼 안전한 실습

먼저 Android Emulator에서 AIDL 기반 앱과 서비스를 만들고, 정상 앱과 권한 없는 앱이 같은 API를 호출하는 상황을 비교한다. 그다음 간단한 “공조 켜기” mock VHAL을 만들어 허용된 호출자만 상태를 바꾸게 한다. 이 단계에서는 실제 차량이나 ECU에 연결하지 않는다. 마지막으로 장비와 저장공간을 확보하면 저자들의 prebuilt image로 Harness 아티팩트의 공격 시뮬레이션과 성능 측정을 재현한다.

3. 연구·프로젝트로 확장할 방향

내가 발전시킨다면 차량 제어 신뢰 경계 시각화 도구를 만들고 싶다. AAOS의 서비스와 Binder 호출 관계를 입력하면 차량 제어 API에 도달하는 경로, 보호 영역에 들어가야 할 구성요소, 신뢰하지 않는 데이터가 경계를 넘는 지점을 표시하는 도구다. 이후 작은 정책 엔진을 붙여 “표시된 버튼에서 시작된 요청인가”, “허용된 서비스가 호출했는가”를 테스트로 검증할 수 있다.

INTERVIEW PITCH

“AAOS가 root 권한까지 침해됐다고 가정해도 차량 제어 앱–CarService–VHAL–HMI를 프로세스 단위 enclave로 격리하는 Harness를 분석했습니다. 보안 효과뿐 아니라 차량 API 22%, Geekbench 3.35%·6.09%의 오버헤드와 실차 미검증이라는 한계까지 함께 비교했습니다.”
