SCOPE

이 글은 하나의 사고를 두 층으로 나눠 본다. 상류의 Trivy 오픈소스 릴리스 인프라가 어떻게 장악됐는지, 그리고 하류 사용자인 유럽연합 집행위원회가 왜 정상 업데이트를 통해 AWS 침해를 당했는지 함께 분석한다.

사건 개요 — 신뢰한 업데이트가 비밀을 수집했다

Trivy는 컨테이너 이미지와 코드의 취약점·설정 오류·비밀을 검사하는 널리 쓰이는 오픈소스 보안 도구다. 2026년 3월 19일 공격 집단 TeamPCP는 Trivy 0.69.4, trivy-action, setup-trivy의 악성 릴리스를 정상 배포 채널에 올렸다. 기존 버전 태그까지 악성 커밋으로 강제 이동시켰기 때문에, 새 버전을 명시적으로 선택하지 않은 CI/CD 파이프라인도 영향을 받을 수 있었다.

유럽연합 집행위원회는 해당 시간대에 손상된 Trivy를 정상 업데이트 경로로 받아 실행했다. 이 과정에서 관리 권한이 있는 AWS 비밀 키가 유출됐다. 공격자는 새 액세스 키를 만들고 추가 비밀을 찾은 뒤, Europa 웹 호스팅 환경에서 약 91.7GB의 압축 데이터를 빼냈다. 3월 28일 ShinyHunters가 이를 다크웹에 공개했다.

항목확인된 내용해석
초기 매개체손상된 Trivy 오픈소스 릴리스사용자는 정상 공급자와 정상 채널을 신뢰했다.
클라우드 자격다른 AWS 계정 관리 권한을 가진 비밀 키CI 도구에 노출된 한 키의 잠재 반경이 컸다.
유출량압축 91.7GB, 비압축 약 340GB탐지 전 대규모 반출이 완료됐다.
영향 범위집행위 내부 고객 42곳 + 다른 EU 기관 최소 29곳공용 호스팅 백엔드가 다기관 위험을 집중시켰다.
서비스 영향변조·중단 징후 없음가용성은 유지됐지만 기밀성은 크게 훼손됐다.

공격자는 77개 중 76개의 trivy-action 태그와 setup-trivy의 모든 7개 태그를 악성 커밋으로 옮겼다. 파일 전체를 난폭하게 바꾸지 않고 진입 스크립트만 교체한 뒤 원래 작성자·이메일·시각·커밋 메시지를 복제했다. 평범한 Git 기록만 보면 정상 변경처럼 보이도록 꾸민 것이다.

특히 @v0나 @0.35.0처럼 이동 가능한 태그를 참조한 GitHub Actions는 워크플로 파일을 수정하지 않았어도 다음 실행부터 다른 코드를 받는다. 이 사건은 버전 번호가 있어 보이는 태그와 변경 불가능한 콘텐츠 식별자가 같은 것이 아님을 드러냈다.

악성 동작 — CI 러너는 비밀이 모이는 장소였다

악성 페이로드는 실행 환경에 따라 수집 방식을 바꿨다. GitHub 호스팅 러너에서는 Runner.Worker 프로세스의 읽을 수 있는 메모리 영역을 덤프해 GitHub Actions가 비밀을 보관하는 내부 패턴을 찾았다. 자체 호스팅 러너에서는 SSH·Git·AWS·GCP·Azure·Kubernetes·Docker·데이터베이스·VPN·TLS 키·지갑 등 50개가 넘는 민감 경로를 훑었다.

수집물은 AES-256-CBC로 암호화되고 세션 키는 공격자의 RSA-4096 공개 키로 감싼 뒤, scan.aquasecurtiy[.]org라는 타이포스쿼팅 도메인으로 전송됐다. 실패하면 피해자의 GitHub 토큰으로 tpcp-docs 공개 저장소를 만들어 릴리스 자산으로 올리는 대체 경로도 사용했다. 정상 Trivy 기능과 악성 동작을 병렬로 실행했기 때문에 빌드 결과만 확인해서는 이상을 눈치채기 어려웠다.

근본 원인 — 취약점 하나가 아닌 다섯 개의 조건

1. 릴리스 자동화의 고권한 토큰이 노출됐다

Aqua Security의 조사에 따르면 출발점은 Trivy GitHub Actions 환경의 설정 오류였다. 공격자는 권한 높은 액세스 토큰을 얻어 저장소 자동화와 릴리스 과정에 발판을 만들었다. 개발 편의를 위해 자동화에 집중된 권한이 공급망 전체를 변조할 권한으로 바뀌었다.

2. 첫 사고 뒤 자격 증명 회전이 완전하지 않았다

Trivy 팀은 3월 1일 앞선 침해를 공개하고 자격 증명을 회전했지만 모든 자격을 동시에 폐기하지는 못했다. 공식 보안 권고는 며칠간 이어진 회전 창에서 아직 유효한 기존 토큰이 새로 발급된 비밀을 다시 탈취했을 가능성을 제시한다. 순차 회전은 공격자에게 새 열쇠를 훔칠 시간을 줄 수 있다. 서비스 계정·봇·워크플로·파생 토큰을 목록화하고 일괄 폐기하지 않으면 회전 자체가 신뢰 회복을 보장하지 못한다.

3. 이동 가능한 태그를 무결성 경계로 사용했다

다수 소비자는 업데이트 편의를 위해 GitHub Action을 태그로 참조했다. 공격자는 새 패키지 이름을 만들 필요 없이 이미 신뢰받는 태그의 목적지만 바꿨다. 태그가 변경될 수 있다는 Git의 특성과, CI가 태그를 사실상 고정 버전으로 받아들이는 운영 관행 사이의 틈이 악용됐다.

4. CI에 장기·고권한 클라우드 비밀이 노출됐다

CERT-EU는 유출된 AWS 키가 다른 집행위 AWS 계정에 대한 관리 권한을 가지고 있었다고 밝혔다. 취약점 스캐너가 클라우드 자격 증명을 볼 수 있는 환경에서 실행됐고, 그 자격은 단일 작업에 필요한 범위를 넘어섰다. 공급망 침해가 곧 클라우드 제어면 침해로 이어진 핵심 증폭 지점이다.

5. 행위 경보는 있었지만 반출 뒤였다

AWS 비밀은 3월 19일 탈취됐고, CSOC가 API 오용·계정 침해·비정상 트래픽 경보를 받은 시점은 24일이었다. 경보가 최종 확산을 막는 데 기여했지만, 약 5일의 체류 시간 동안 대량 반출은 완료됐다. 실행 직후의 비정상 비밀 접근과 낯선 외부 통신을 CI 계층에서 차단하지 못했다.

대응 평가 — 범위를 좁혔지만 유출은 되돌릴 수 없었다

유럽연합 집행위원회는 3월 24일 경보 후 사고 대응을 시작하고, 다음 날 손상된 AWS 비밀을 보호한 뒤 공격자가 만든 키를 비활성화했다. CERT-EU와 개인정보 보호 책임자, 유럽개인정보보호감독기구에 통보하고 영향받은 기관과 직접 회의를 시작했다. 조사에서는 다른 AWS 계정으로의 횡적 이동 징후와 웹사이트 변조·중단은 발견되지 않았다.

Aqua Security는 악성 릴리스와 이미지를 제거하고 태그를 안전한 커밋으로 복구했으며, 자동화·서비스 계정·토큰을 전면 잠갔다. 장기 자격 증명 의존 축소, 릴리스 출처 증명, 변경 불가능한 릴리스 검증도 도입하기로 했다. 안전한 버전, 해시, 도메인과 IP, 파일 경로 등 구체적인 IOC를 공개해 하류 사용자가 자체 조사를 할 수 있게 한 점은 긍정적이다.

다만 봉쇄 시점에는 91.7GB의 데이터가 이미 조직 밖에 있었고 사흘 뒤 공개됐다. 키 폐기와 시스템 정리는 추가 접근을 막지만, 복제된 데이터의 기밀성을 회복하지 못한다. 공급망 사고에서는 탐지 후 복구보다 실행 전 신뢰 검증과 실행 중 권한 제한이 더 중요하다.

보완이 미흡했던 부분 — ‘업데이트하고 키를 돌리라’ 다음 단계

  • 초기 회전의 완전성을 증명하지 못했다. 남아 있는 모든 토큰과 파생 권한을 식별하는 자격 증명 인벤토리가 부족했다.
  • 태그 복구만으로 과거 실행을 안전하게 만들 수 없다. CI 캐시·아티팩트·포크·자체 호스팅 러너의 지속성까지 별도로 조사해야 한다.
  • 전체 SHA 고정만으로 충분하지 않다. 고정한 커밋 자체가 악성이면 보호되지 않으므로 출처 증명·서명·검토·업데이트 절차가 함께 필요하다.
  • EU 환경의 키 설계 개선이 구체적으로 공개되지 않았다. 장기 키를 OIDC 기반 단기 세션으로 교체했는지, 관리 권한을 얼마나 축소했는지 알 수 없다.
  • 공용 호스팅의 집중 위험이 남는다. 한 AWS 계정의 침해가 71개 고객 데이터로 이어진 만큼 테넌트·기관별 격리 수준을 재검토해야 한다.

CORE LESSON

공급자를 신뢰하는 것과 공급자가 배포한 매 실행물을 무조건 신뢰하는 것은 다르다. 외부 코드가 손상될 수 있다고 가정하고도 비밀을 읽지 못하고, 장기 권한을 얻지 못하고, 허용되지 않은 곳으로 통신하지 못하게 해야 피해 반경이 작아진다.

근거 자료와 한계

사건 귀속은 CERT-EU와 Aqua Security가 공개한 평가를 따랐다. CERT-EU는 Trivy 공급망 침해가 초기 경로였다고 높은 신뢰도로 평가했지만, 모든 데이터베이스의 개인정보 영향 분석은 발표 당시에도 진행 중이었다. 따라서 이 글은 확인된 최소 영향과 공개된 기술 경로를 중심으로 작성했다.
