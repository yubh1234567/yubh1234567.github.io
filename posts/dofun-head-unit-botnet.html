SCOPE FIRST

이 사례는 DoFun 소프트웨어를 사용하는 일부 Android 기반 차량 헤드유닛의 문제다. 스마트폰 화면을 차량에 연결하는 Android Auto 전체나 Google의 Android Automotive OS 전체가 감염됐다는 뜻이 아니다. 또한 공개 분석에는 조향·제동·CAN 같은 핵심 차량 제어가 탈취됐다는 증거가 없다.

사건 개요 — ‘업데이트’라는 신뢰가 악성코드의 배달원이 됐다

Kaspersky는 2026년 6월 Android 위협을 추적하던 중 사용자 화면이 전혀 없는 JarService 앱을 발견했다. 분석 결과 이 앱은 일반 스마트폰이 아니라 차량의 Android 헤드유닛에 설치됐고, 사용자가 직접 내려받은 것도 아니었다. DoFun 펌웨어의 합법적인 시스템 앱 TWCore가 제조사 클라우드의 지시를 받아 자동 설치했다.

이는 차량 헤드유닛에 특화된 감염 체인을 통해 악성코드가 배포된 최초의 문서화 사례로 소개됐다. 연구진의 실험에만 머문 취약점이 아니라, 실제 공격자가 광고 사기와 프록시 봇넷 구축을 위해 운영한 인더와일드 악성 캠페인이다. 감염된 장치는 공격자 대신 웹 요청을 보내고 다른 코드를 실행하며, 자동차의 데이터 회선과 공인 IP를 빌려 주는 노드가 됐다.

항목확인된 내용과장하면 안 되는 부분
대상DoFun 소프트웨어가 탑재된 일부 Android 기반 헤드유닛모든 Android 차량 시스템의 문제가 아니다.
유포 경로합법적 시스템 업데이트 앱 TWCore정확히 어떤 서버 권한이 어떻게 장악됐는지는 공개되지 않았다.
최종 목적광고 사기, 추가 코드 실행, zhima 프록시 봇넷핵심 차량 제어 침해는 확인되지 않았다.
행위자BADBOX와 연계된 MoYu Group에 높은 신뢰도로 귀속기술·인프라 겹침에 기반한 분석적 판단이다.
영향 규모정확한 감염 대수·모델·국가는 미공개DoFun의 ‘3천만 사용자’ 주장을 감염 대수로 쓰면 안 된다.

“항상 최신 버전으로 업데이트하라”는 보안 조언은 대체로 옳다. 하지만 이번 사건에서는 업데이트를 수행하는 주체가 공격 전달 경로였다. 따라서 차량·IoT 공급망에서는 최신 여부만큼 누가 어떤 키로 무엇을 승인했고, 기기가 설치 전에 무엇을 검증했는지가 중요하다.

1. TWCore — 너무 많은 신뢰를 가진 정상 앱

TWCore는 분석 데이터를 수집하고 헤드유닛 소프트웨어를 갱신하는 합법적인 시스템 앱이다. MQTT 메시지 브로커가 설치할 APK 정보를 보내면 파일을 내려받아 설치했다. 분석된 메시지에는 기존 앱의 업데이트뿐 아니라 기기에 없던 새 앱까지 설치하도록 허용하는 조건이 있었다. Kaspersky 텔레메트리에서 악성 파일은 일관되게 TWCore의 패키지명이 설치 주체로 기록됐다. 사용자 클릭이나 별도 동의 화면은 필요하지 않았다.

2. JarService와 로더 — 작고 조용한 첫 단계

JarService에는 아이콘이나 UI가 없었다. 내부에 암호화해 둔 다음 단계 코드와 실행 정보를 풀어 로더를 실행하는 것이 목적이었다. 로더는 공격자 C2에 현재 임플란트 정보를 보내고 다음 페이로드의 주소를 받아 내려받아 복호화·실행했다. 작은 1단계만 신뢰 경로로 넣고 나머지를 서버에서 바꾸는 구조는 탐지 회피와 기능 교체에 유리하다.

3. 클리커와 zhima — 자동차를 돈 버는 네트워크 자원으로 바꿨다

3단계는 주기적으로 화면 해상도, 장치 모델, MAC 주소, 연결된 Wi-Fi 정보 등을 C2에 보냈다. 분석 당시 구현된 명령은 웹 요청, WebView 동작, 추가 코드 다운로드·실행 등을 포함했다. 실제 관찰된 핵심 페이로드 중 하나인 zhima는 외부 트래픽을 감염 기기를 통해 전달하는 역방향 프록시였다. 공격자는 차량을 훔치기보다 차주의 통신비·IP 평판·연산 자원을 조용히 수익화했다.

4. 왜 자동차 헤드유닛이 매력적인가

헤드유닛은 오랫동안 켜져 있고, SIM이나 Wi-Fi로 인터넷에 연결되며, 사용자는 스마트폰보다 설치 앱과 네트워크 사용량을 덜 살핀다. 자동차마다 다른 지역의 이동통신망을 이용하므로 프록시 사업자에게는 다양한 출구 IP를 제공한다. 화면이 느려지거나 데이터가 소모돼도 운전자는 노후화나 통신 품질 문제로 오해하기 쉽다.

근본 원인 — 서명 없는 명령보다 ‘무제한 설치 권한’이 더 큰 문제다

1. 업데이트 권한의 범위가 지나치게 넓었다

업데이트 앱은 이미 설치된 구성요소를 정해진 서명으로 교체하는 수준을 넘어, 서버 메시지만으로 새로운 앱을 넣을 수 있었다. 패키지명·서명 인증서·버전·대상 장치가 허용 목록과 일치하는지 기기 스스로 확인하지 못하면 서버 한 곳의 오용이 전체 단말의 임의 코드 실행으로 확대된다.

2. 서버의 신뢰가 곧 소프트웨어의 신뢰가 됐다

공개 분석은 공격자가 브로커나 배포 인프라를 정확히 어떻게 장악했는지 단정하지 않는다. 그러나 결과적으로 단말은 “신뢰된 채널에서 온 설치 지시”를 “설치해도 안전한 코드”와 동일하게 취급했다. 채널 인증, 메타데이터 서명, APK 서명, 투명한 승인 기록이 서로 독립된 검증 계층이어야 했지만 한 경로의 권한으로 수렴했다.

3. 고권한 시스템 앱에 최소 권한과 사용자 가시성이 부족했다

TWCore는 분석 수집과 소프트웨어 설치를 함께 담당했다. 원격 지시로 앱을 설치하는 강한 기능이 백그라운드에서 동작했고, 차주는 어떤 구성요소가 언제 추가됐는지 확인하기 어려웠다. 시스템 앱이 필요하더라도 설치 정책과 분석 수집은 분리하고, 변경 이력과 복구 경로를 제공해야 한다.

4. 인포테인먼트 공급망의 자산 식별이 불투명했다

DoFun은 펌웨어·앱·클라우드를 여러 헤드유닛 제품에 공급한다. 소비자는 완성차 로고나 판매자 이름만 알고 실제 펌웨어 공급자를 모를 수 있다. 어떤 모델과 버전이 같은 업데이트 백엔드를 쓰는지 목록이 없으면 사고가 발생해도 통지, 패치, 감염 확인, 중고차 소유권 이전을 끝까지 추적하기 어렵다.

대응 평가 — IOC 공개는 유용하지만 “수정했다”만으로는 부족하다

Kaspersky는 DoFun에 감염 유포 구조를 알렸고, DoFun은 발견된 보안 문제를 수정했다고 회신했다. 연구진은 JarService, 단계별 로더, zhima 모듈, C2와 배포 주소에 대한 IOC와 탐지명을 공개했다. 보안 제품과 네트워크 운영자가 이미 감염된 단말을 찾을 수 있는 실질적인 단서라는 점에서 의미가 있다.

그러나 배포 서버를 막는 것과 감염 단말을 깨끗하게 만드는 것은 다른 일이다. 공격자는 추가 코드를 실행할 수 있었으므로 JarService 하나를 지웠다고 완전한 복구를 보장할 수 없다. 알려진 정상 이미지로 재설치하고 부팅·시스템 파티션 무결성을 확인한 뒤, C2 통신이 더 이상 없는지 검증하는 절차가 필요하다.

보완이 미흡했던 부분 — 내 차가 대상인지 알 방법이 없다

  • 정확한 모델·버전·국가·감염 대수가 공개되지 않았다. DoFun의 서비스 규모는 잠재적 공급 범위일 뿐 실제 감염 규모가 아니다.
  • ‘수정’의 내용과 배포 버전이 없다. 브로커 인증, APK 검증, 키 교체, 서버 폐쇄 중 무엇이 바뀌었는지 외부에서 확인할 수 없다.
  • 초기 침해 원인이 남아 있다. 공격자가 합법적 배포 경로에 설치 지시를 넣은 최초 단계가 공개되지 않아 같은 경로의 재발 가능성을 평가하기 어렵다.
  • 이미 감염된 장치의 정리 여부가 불명확하다. 업데이트 서버를 고쳐도 기존 로더와 추가 페이로드가 자동으로 사라지는 것은 아니다.
  • 차주의 확인·복구 절차가 없다. 일반 사용자가 펌웨어 공급자, TWCore 버전, 설치 이력, 네트워크 이상을 확인할 공식 안내가 부족하다.
  • 차량 네트워크 분리 상태가 공개되지 않았다. 이번에는 봇넷이 목적이었지만, 헤드유닛이 차량 기능과 연결된 만큼 최소 권한 게이트웨이 검증이 필요하다.

방어 설계 — 업데이트 서버도 틀릴 수 있다고 가정하라

계층필수 통제이번 사건에서 막는 지점
배포오프라인 루트 키와 역할 분리된 서명 메타데이터, 만료·롤백·동결 공격 방어서버 지시 하나로 임의 APK가 신뢰되는 문제
단말허용 패키지명·서명 인증서·해시·버전 범위를 기기에서 재검증기존에 없던 JarService 설치
업데이터분석과 설치 역할 분리, 최소 권한, 새 앱 설치는 별도 승인 정책 적용TWCore 권한의 단일 실패점
통신상호 TLS, 장치별 인증서, MQTT 토픽별 ACL, 키 교체와 비정상 대량 지시 탐지브로커 또는 배포 채널 오용
플랫폼Verified Boot·읽기 전용 시스템 파티션·앱 실행 무결성 측정지속성 확보와 변조 은폐
네트워크필요 목적지로만 나가는 egress 허용 목록, 프록시·C2 패턴과 데이터 급증 탐지zhima 봇넷 통신과 추가 페이로드
차량헤드유닛과 안전 관련 ECU 사이의 메시지·명령 허용 목록형 보안 게이트웨이인포테인먼트 침해의 차량 제어 영역 확산
운영모델·펌웨어·공급자 SBOM, VIN 기반 통지, 정상 이미지 재설치와 사후 검증대상 식별과 감염 장치 정리 공백

자동차 업데이트에는 TUF/Uptane 계열의 설계 원칙이 특히 유용하다. 저장소나 온라인 키 일부가 침해돼도 단일 역할이 마음대로 새 소프트웨어를 배포하지 못하게 하고, 오래된 취약 버전으로 되돌리거나 업데이트를 무기한 멈추는 공격까지 고려하기 때문이다. 중요한 것은 특정 프레임워크 이름보다 서버를 신뢰하되, 서버만 믿지는 않는 검증 구조다.

CORE LESSON
