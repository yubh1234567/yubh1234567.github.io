이 사례는 범죄자가 실제 고객 차량을 공격한 침해 사고가 아니라, Sam Curry와 Shubham Shah가 허가받은 차량으로 검증한 뒤 제조사에 알린 책임 있는 취약점 공개다. 공개 자료에는 제3자의 선행 악용 증거가 없다. 따라서 이 글은 “가능했던 피해”와 “실제로 검증한 범위”를 구분한다.

사례의 성격 — 클라우드 계정이 사실상 디지털 자동차 키였다

2026년 초, 연구진은 이름이 공개되지 않은 두 자동차 제조사의 모바일 앱을 분석했다. 두 회사는 고객 로그인과 계정 정보를 관리하기 위해 ForgeRock 계열의 Access Management와 OpenIDM을 사용했다. 문제는 차량 자체가 아니라 이 인터넷 공개 인증 기반에 있었다. 연구진은 경계 장비가 차단한다고 믿었던 관리 콘솔에 도달했고, 문서에 명시된 초기 자격 증명 admin:admin으로 로그인했다.

관리 콘솔에서 본격적인 문제는 시작됐다. OpenIDM의 스케줄러와 스크립트 실행 기능을 통해 운영 서버의 프로세스에서 코드를 실행할 수 있었고, 서버 내부에서 고객 디렉터리에 접근해 시험 계정의 이메일과 비밀번호를 바꿀 수 있었다. 그 뒤에는 공격용 비밀 API가 필요하지 않았다. 정상 앱의 인증 흐름으로 로그인해 정상 OAuth 토큰을 발급받고, 앱에 원래 있던 차량 명령을 사용하면 됐다.

구분확인된 사실해석할 때 주의할 점
영향 대상ForgeRock 기반 로그인을 사용한 익명의 두 제조사제조사·차종·정확한 고객 수는 공개되지 않았다.
실차 검증소유 또는 명시적 허가를 받은 미국 차량“모든 차량을 실제로 열었다”는 뜻이 아니다.
가능한 기능위치·주행 정보 조회, 잠금/해제, 시동/정지, 경적·비상등 등차종과 구독 서비스에 따라 명령 범위가 달랐다.
대응보고 후 약 2시간 안에 양사 수정, 관련 자격 증명 교체호주 환경의 별도 공격 체인은 정확한 수정 시점이 공개되지 않았다.
악용 여부연구진 외 제3자 악용은 공개 자료에서 확인되지 않음악용이 없었다는 증명과 로그 조사 결과 공개는 서로 다르다.

“최근 1년 사례”라는 기준에서 중요한 날짜는 공개일만이 아니다. 연구와 수정은 2026년에 이뤄졌고, 11월 7일 상세 분석이 공개됐다. 제조사가 공개되지 않은 것은 연구진이 밝힌 선택이며, 이 때문에 차주가 자신의 차량이 범위에 포함됐는지 외부 정보만으로 판단하기는 어렵다.

1. 서로 다르게 읽힌 경로

외부 WAF는 민감한 OpenIDM·관리 경로를 막고 있었다. 하지만 URL 인코딩 문자, 경로 구분자, 세미콜론 매개변수를 경계 장비와 뒤쪽 Java/Jetty 계층이 서로 다르게 정규화했다. 앞단에는 정적 파일처럼 보인 요청이 백엔드에서는 Apache Felix 관리 콘솔 경로로 해석됐다. 이는 단순한 “WAF 규칙 누락”보다 위험한 파서 불일치다.

2. 운영에 남은 개발 콘솔과 초기 비밀번호

관리 콘솔은 존재만으로도 강력한 운영 기능을 노출한다. PingIDM 보안 가이드는 프로덕션 배포 전에 Felix 콘솔을 제거하거나 보호하라고 명시하고, 콘솔 인증은 IDM 인증과 통합되지 않는다고 경고한다. 그런데 대상 환경에서는 콘솔이 남아 있었고 별도 인증에는 기본값 admin:admin이 유지됐다. WAF라는 얇은 가림막이 사라지자 다음 방어선이 없었다.

3. 관리 기능이 곧 코드 실행 권한이 됐다

콘솔 접근 후 연구진은 OpenIDM 스케줄러가 실행하는 스크립트를 이용해 운영 프로세스의 권한으로 명령을 수행했다. 인터넷에서 직접 막힌 고객 데이터도 서버 내부의 로컬 인터페이스에서는 접근 가능했다. “외부에서는 403”이라는 통제가 서버 자체가 장악된 뒤에도 데이터를 보호해 주지는 못한 것이다.

4. 계정 장악이 차량 권한으로 자동 승격됐다

시험 계정의 이메일과 비밀번호를 변경한 뒤 정상 인증 흐름을 거치자 앱 토큰이 발급됐다. 토큰으로 차고에 등록된 차량, VIN과 텔레메트리를 조회하고 차종·구독에 허용된 원격 명령을 호출할 수 있었다. 연구진은 차주가 지켜보는 차량에서 문을 열고 시동을 켰다가 끈 뒤 다시 잠그는 전체 과정을 검증했다. 서버는 명령을 “침입자의 요청”이 아니라 정상 계정이 보낸 정당한 요청으로 보았다.

별도 호주 체인 — 테스트 자산과 운영 환경의 경계 붕괴

호주 환경에서는 다른 길이 발견됐다. 공개 인터넷의 TEST HARNESS 관리 도구와 JavaScript 번들에 포함된 API 키를 통해 차량 번호판에서 VIN, 가입자 식별자, 계정 정보로 이어지는 조회가 가능했다. 스테이징용으로 보이는 OpenIDM 관리자 자격 증명도 운영 환경에서 작동했고, WAF 경로 우회와 구식 Resource Owner Password Credentials 흐름의 조합으로 MFA를 건너뛴 앱 토큰을 만들 수 있었다. 연구진이 정리한 체인은 번호판 → 계정 → 토큰 → 차량 명령으로 이어졌다.

근본 원인 — 기본 비밀번호 하나보다 큰 구조적 실패

1. 프로덕션 하드닝이 배포 조건이 아니었다

초기 비밀번호가 직접적인 진입점이었지만, 더 근본적인 문제는 제거해야 할 개발·디버그 기능이 운영 환경에 남아도 배포가 통과됐다는 점이다. 제품 문서에 이미 적힌 하드닝 항목이 체크리스트에만 있고 자동 검증되지 않으면, 시간이 지나면서 언젠가 다시 같은 설정이 생긴다.

2. WAF를 보안 경계로 과신했다

관리 콘솔과 OpenIDM을 인터넷에서 분리하는 대신 URL 패턴 차단에 의존했다. 하지만 요청은 CDN, 프록시, WAF, 서블릿 컨테이너, 애플리케이션을 지나며 여러 번 해석된다. 각 계층의 정규화 결과가 다르면 “차단한 문자열”과 “실제로 실행된 리소스”가 달라진다. 관리면을 공개 데이터면과 같은 경로에 둔 설계 자체가 취약했다.

3. 고객 신원과 차량 명령의 권한이 너무 가깝게 연결됐다

로그인 계정이 탈취되면 민감 정보 조회뿐 아니라 잠금 해제와 시동까지 같은 신뢰 체인으로 허용됐다. 차량 명령에 별도의 최근 재인증, 등록된 물리 키의 증명, 차량 근접성 확인, 거래 서명이 있었다면 인증 서버 하나의 침해가 곧바로 물리 기능까지 전파되는 것을 줄일 수 있었다.

4. 개발·스테이징·운영의 비밀과 도구가 섞였다

호주 체인의 하드코딩 API 키와 운영에서 작동한 스테이징 관리자 정보는 환경 분리 실패를 보여 준다. 브라우저나 앱에 전달되는 번들은 사용자가 모두 읽을 수 있으므로 관리자 비밀의 저장소가 될 수 없다. 테스트 도구 역시 운영 고객·차량에 연결되는 순간 테스트 자산이 아니라 운영 공격면이다.

대응 평가 — 두 시간의 봉쇄는 좋았지만 그다음이 보이지 않는다

보고 후 약 두 시간 만에 두 제조사가 공격 체인을 막고 관련 자격 증명을 교체한 것은 매우 빠른 초기 대응이다. 연구진이 전체 체인을 허가 차량으로만 검증했고 원래 계정 정보를 복구한 점도 피해를 제한했다. 명확한 재현 절차를 받은 제조사가 즉시 위험을 이해하고 조치할 수 있었던 책임 공개의 좋은 사례다.

다만 “수정”은 URL 하나를 막거나 비밀번호를 바꾸는 것으로 끝나지 않아야 한다. 콘솔 제거, 세션·토큰 전면 무효화, 과거 로그에서 유사 경로와 비정상 스케줄러 변경 탐색, 관리자 비밀 회전, 고객 계정 변경 이력 검토까지 포함돼야 한다. 공개 자료는 자격 증명 교체 외의 상세 범위를 제공하지 않는다.

보완이 미흡했던 부분 — 차주는 무엇을 확인할 수 있었나

  • 제조사와 차종이 비공개다. 보안팀에는 협조적일 수 있지만, 차주가 자신의 노출 여부와 안내·보상 필요성을 판단하기 어렵다.
  • 과거 악용 조사 결과가 없다. 제3자 악용 증거가 공개되지 않았지만, 관련 로그 보존 기간과 위협 헌팅 범위도 알 수 없다.
  • 기존 토큰과 세션의 처리 여부가 불명확하다. 비밀번호·이메일 변경 뒤에도 소유자 앱 세션이 유지됐고 알림 목적지를 바꿀 수 있었다는 점은 세션 수명주기 문제를 드러낸다.
  • 호주 환경의 수정 시점과 조치가 공개되지 않았다. 미국 체인과 다른 경로였으므로 별도의 폐쇄 확인이 필요하다.
  • 차량 명령 자체의 2차 승인 개선이 보이지 않는다. 로그인 인프라를 고쳐도 다른 계정 탈취 경로가 생기면 같은 결과가 반복될 수 있다.
