ERC-1271
컨트랙트도 서명자가 되는 방법

일반 지갑은 비밀 열쇠인 개인키로 서명한다. 그런데 여러 사람이 함께 관리하는 스마트 지갑에는 대표 개인키가 하나만 있는 것이 아니다. 그렇다면 앱은 그 지갑이 정말 동의했는지 어떻게 확인할까? 먼저 지갑·주소·개인키·서명의 뜻부터 알아보고, ERC-1271이 이 문제를 어떻게 해결했는지 Safe의 실제 메인넷 코드와 함께 살펴본다.

핵심 요약

  • 일반 지갑은 개인 도장처럼 개인키 하나로 서명하지만, 스마트 지갑은 여러 사람의 승인 같은 자체 규칙을 사용한다.
  • ERC-1271은 앱이 스마트 지갑에 isValidSignature로 “이 서명을 인정하나요?”라고 묻는 방법을 정한다.
  • Safe에서는 현재 등록된 소유자와 필요한 승인 수를 검사하므로, 구성원이 바뀌면 같은 서명의 판정도 달라질 수 있다.

먼저 알아둘 것 — 지갑은 코인을 담는 가방이 아니다

이더리움은 여러 컴퓨터가 같은 거래 기록과 프로그램을 함께 관리하는 네트워크다. 이 안에서 계정을 구분하는 문자열이 주소다. 은행의 계좌번호처럼 받을 곳을 가리키지만, 주소만 안다고 그 계정의 자산을 움직일 수는 없다.

지갑은 코인을 파일처럼 보관하는 가방이라기보다, 계정을 사용할 권한을 관리하고 이더리움에 명령을 보내는 도구다. 자산 기록은 블록체인에 있고, 일반 지갑은 그 기록을 바꿀 수 있는 비밀값인 개인키를 관리한다. 개인키는 절대 공개해서는 안 되는 비밀 도장이라고 생각하면 된다.

서명은 개인키 자체를 보여 주지 않고도 “이 계정의 주인이 이 내용에 동의했다”는 것을 증명하는 값이다. 수표에 도장을 찍는 것과 비슷하지만, 서명 대상이 조금만 달라져도 결과가 완전히 달라진다. 따라서 송금액이나 주문 내용이 바뀌면 기존 서명을 그대로 쓸 수 없다.

ERC-1271은 두 번째 경우를 위한 표준이다. 컨트랙트 지갑의 복잡한 내부 규칙을 모든 앱이 직접 이해하는 대신, 그 지갑에 “이 서명을 회사 규정상 인정하나요?”라고 같은 방식으로 물을 수 있게 한다.

왜 필요했나 — 개인 도장 검사만으로는 공동 계좌를 확인할 수 없다

이더리움의 일반 사용자 계정인 EOA(Externally Owned Account)는 개인키로 전자서명을 만든다. 앱은 ecrecover라는 이더리움 기능으로 서명에서 주소를 찾아내고, 그 주소가 주장한 사람과 같은지 비교한다. 쉽게 말해 개인 도장이 등록된 사람의 것인지 검사하는 방식이다.

스마트 컨트랙트 계정은 전제가 다르다. 그 주소는 프로그램과 저장된 규칙을 가리킬 뿐, 주소에 대응하는 대표 개인키가 하나만 있지 않다. 3명 중 2명의 승인을 요구할 수도 있고, 특정 기기에는 소액 결제 권한만 줄 수도 있으며, 소유자를 교체할 수도 있다. 회사 공동 계좌를 직원 한 명의 개인 도장만으로 확인할 수 없는 것과 같다.

ERC-1271은 2018년 이 차이를 해결하기 위해 제안됐고 현재 Final 상태의 ERC 표준이다. EIP 사이트에서 관리되지만 지갑과 앱 사이의 공통 사용법을 정하므로 공식 이름은 ERC-1271이다. 핵심은 “서명에서 개인을 찾아내기” 대신 “컨트랙트 지갑에 직접 물어보기”로 검증 방향을 바꾼 것이다.

표준은 무엇을 정했나 — 질문과 성공 신호만 통일했다

ERC-1271이 정한 함수는 하나뿐이다. 여기서 인터페이스란 서로 다른 프로그램이 같은 방식으로 대화하도록 맞춘 함수 이름과 입력·출력 규칙을 뜻한다. 은행마다 내부 시스템은 달라도 잔액 조회 버튼의 역할은 같은 것과 비슷하다.

함수는 검증할 해시(hash)와 서명을 입력받는다. 해시는 긴 주문서나 메시지를 고정 길이의 값으로 압축한 디지털 지문이다. 원문이 한 글자만 달라져도 지문이 달라지므로, 서명한 내용이 바뀌지 않았는지 확인하는 데 쓴다. 컨트랙트 지갑은 자체 승인 규칙을 검사한 뒤 정해진 성공값을 돌려준다.

IERC1271.solMINIMAL INTERFACE
interface IERC1271 {
    function isValidSignature(bytes32 hash, bytes calldata signature)
        external
        view
        returns (bytes4 magicValue);
}

bytes4 constant MAGIC_VALUE = 0x1626ba7e;
// bytes4(keccak256("isValidSignature(bytes32,bytes)"))

왜 bool이 아니라 매직값일까

유효한 서명이라면 함수는 0x1626ba7e를 반환한다. 이런 미리 약속한 특수값을 매직값이라고 부른다. 평범한 참·거짓 대신 함수 이름에서 계산한 고유 값을 사용해 “ERC-1271 규칙에 따라 성공했다”는 사실을 더 분명하게 표시한다. 다른 값, 빈 응답, 오류는 모두 유효하지 않은 서명으로 처리한다.

왜 상태를 바꾸면 안 될까

서명을 확인하는 행위가 자산을 옮기거나 설정을 바꾸면 위험하다. 그래서 ERC-1271은 isValidSignature가 블록체인 상태를 변경하지 않아야 한다고 규정한다. 코드에서는 view로 표시하고, 호출할 때는 STATICCALL이라는 읽기 전용 방식을 사용한다. 은행 직원이 서명만 확인해야지 그 과정에서 잔액을 바꾸면 안 되는 것과 같다.

읽기 전용이라고 해서 내부 검사가 단순한 것은 아니다. 지갑은 현재 소유자 목록이나 시간 조건을 확인하고 여러 사람의 서명을 조합할 수 있다. ERC-1271이 통일한 것은 질문하는 방법과 성공 신호다. 실제 승인 규칙은 각 지갑이 정한다.

검증은 어떻게 흐르나 — 서명자 유형을 먼저 나눈다

토큰 주문을 처리하는 거래소 프로그램을 예로 들어 보자. 주문에는 어떤 토큰을 얼마나 거래할지, 언제까지 유효한지, 같은 주문이 두 번 실행되지 않게 하는 일회용 번호인 nonce가 들어 있다. 앱은 이 내용을 해시로 만든다. 주문자가 일반 지갑이면 개인 서명 경로를, 컨트랙트 지갑이면 ERC-1271 경로를 이용한다.

아래 코드는 개발자가 흐름을 확인하기 위한 축약 예시다. 코드를 몰라도 “주소에 프로그램이 없으면 일반 지갑 방식, 있으면 ERC-1271 방식”으로 나뉜다는 점만 이해하면 된다. 실제 서비스에서는 검증된 라이브러리와 충분한 실패 처리가 필요하다.

INTEGRATIONSOLIDITY-LIKE PSEUDOCODE
function valid(address signer, bytes32 digest, bytes calldata sig)
    internal view returns (bool)
{
    if (signer.code.length == 0) {
        return ECDSA.recover(digest, sig) == signer;
    }

    (bool ok, bytes memory out) = signer.staticcall(
        abi.encodeCall(IERC1271.isValidSignature, (digest, sig))
    );

    return ok
        && out.length >= 32
        && abi.decode(out, (bytes4)) == 0x1626ba7e;
}

한 가지 예외도 있다. 주소는 미리 정했지만 지갑 프로그램은 아직 블록체인에 올리지 않은 계정이다. 이를 배포 전 스마트 계정 또는 카운터팩추얼 계정이라고 한다. 현재는 코드가 없어 일반 지갑처럼 보일 수 있으므로, 이런 서명을 확인하는 ERC-6492 같은 별도 표준이 필요하다.

메인넷의 Safe 사례 — 공유 핸들러가 각 계정의 규칙을 읽는다

Safe Smart Account는 여러 사람이 공동 자산을 관리할 수 있는 스마트 지갑이다. Safe는 소유자 목록과 거래에 필요한 최소 승인 수를 저장한다. 예를 들어 소유자 3명 중 2명의 승인이 필요하도록 정할 수 있다. 이때 필요한 최소 승인 수를 임계값이라고 한다.

Safe v1.4.1은 CompatibilityFallbackHandler라는 보조 프로그램에 ERC-1271 검증 기능을 구현한다. 이름은 어렵지만 역할은 안내 데스크와 비슷하다. Safe 계정이 직접 처리하지 않는 서명 확인 요청을 이 보조 프로그램으로 전달하고, 보조 프로그램은 요청을 보낸 Safe의 현재 소유자와 임계값 규칙을 검사한다.

여러 Safe가 같은 보조 프로그램 코드를 공유해도 각 Safe의 소유자와 승인 규칙은 서로 다르다. 따라서 검증자는 보조 프로그램 주소가 아니라 실제로 서명자로 주장된 Safe 계정 주소에 질문해야 한다.

이 구조 덕분에 외부 앱은 Safe 내부에서 서명을 어떤 순서로 묶는지까지 알 필요가 없다. 표준 함수로 질문하고 결과만 받으면 된다. 다만 소유자가 교체되거나 필요한 승인 수가 바뀌면 예전에 통과하던 서명이 더 이상 통과하지 않을 수 있다. 컨트랙트 서명 검증은 영원히 변하지 않는 증명이라기보다 현재 지갑 규칙에 대한 질문이다.

EIP-712·ERC-4337과의 관계 — 만드는 법, 판정하는 법, 실행하는 법

번호가 비슷해 보여도 세 표준의 역할은 다르다. 문서를 작성하는 규칙, 회사 도장을 확인하는 규칙, 승인된 업무를 실제로 전달하는 규칙에 각각 가깝다.

ERC-4337스마트 지갑의 실행 요청과 가스비를 어떻게 전달·처리할까?승인된 업무를 실행 시스템으로 보내는 규칙

EIP-712와 ERC-1271은 함께 쓸 수 있다. EIP-712로 “어떤 토큰을, 얼마까지, 누구에게 허용한다”처럼 사람이 확인할 수 있는 서명 문서를 만들고, ERC-1271로 컨트랙트 지갑이 그 문서를 승인했는지 묻는다. 같은 서명을 다른 서비스에서 다시 쓰지 못하게 하려면 네트워크 번호, 대상 프로그램, 일회용 번호와 만료 시각도 문서에 포함해야 한다.

ERC-4337은 더 큰 실행 흐름을 다룬다. 스마트 지갑이 만든 요청을 중계자가 모으고, EntryPoint라는 공통 프로그램을 통해 실행하는 방법을 정한다. ERC-1271과 비슷한 승인 규칙을 내부에서 재사용할 수 있지만 둘은 별도 표준이다. ERC-1271을 지원한다고 자동으로 ERC-4337 지갑이 되는 것도 아니고, ERC-4337 지갑이 반드시 ERC-1271을 제공해야 하는 것도 아니다.

안전하게 연동하기 — 매직값 비교보다 넓은 경계를 본다

처음 읽는 사람이라면 세 가지만 기억하면 된다. 성공값을 정확히 확인하고, 무엇에 서명했는지 함께 확인하며, 컨트랙트 지갑의 구성은 나중에 바뀔 수 있다는 점이다. 아래는 실제 서비스를 만드는 개발자가 확인할 세부 항목이다.

  • 정확한 성공값만 허용한다. 함수 호출이 끝났다는 사실만 보지 말고 0x1626ba7e가 돌아왔는지 비교한다. 오류나 해석할 수 없는 응답은 실패로 처리한다.
  • 읽기 전용으로 호출한다. STATICCALL을 사용해 서명 확인 과정에서 블록체인 상태가 바뀌지 않게 한다.
  • 서명한 내용을 함께 확인한다. 어느 네트워크와 앱에서, 어떤 작업을, 몇 번째로, 언제까지 허용했는지를 해시에 묶어 다른 곳에서의 재사용을 막는다.
  • 판정 시점을 기록한다. 컨트랙트 지갑의 소유자와 승인 규칙은 바뀔 수 있다. 당시 유효성을 나중에 증명해야 한다면 검사한 블록 번호도 보존한다.
  • 한 번의 실패가 전체 서비스를 멈추지 않게 한다. 외부 지갑은 오류를 내거나 지나치게 많은 계산을 요구할 수 있으므로 여러 주문을 처리할 때 실패 범위를 제한한다.
  • 아직 배포되지 않은 지갑을 구분한다. 코드가 없다고 무조건 일반 지갑으로 판단하지 말고, 제품이 배포 전 스마트 계정을 지원한다면 ERC-6492도 별도로 검토한다.

지갑을 만드는 쪽도 서명 형식과 해시 처리 방식을 명확히 문서화하고 잘못된 길이의 입력을 거부해야 한다. 업그레이드할 수 있는 지갑이라면 프로그램이나 보조 검증기를 바꿨을 때 과거 서명의 판정이 어떻게 달라지는지도 시험해야 한다.

배운 점 — 서명은 수학식이면서 계정의 정책이다

일반 지갑의 서명은 개인 도장을 확인하는 문제에 가깝다. 스마트 컨트랙트 지갑에서는 “누가 몇 명이나 동의해야 하는가”를 프로그램이 정한다. ERC-1271은 이 복잡한 회사 규정을 개인 도장 하나처럼 억지로 바꾸지 않고, 외부 앱이 같은 질문으로 승인 결과를 확인하게 했다.

표준이 고정한 것은 질문할 함수와 성공값뿐이다. 그래서 어떤 지갑은 두 사람의 서명을 요구하고, 다른 지갑은 보안 키나 시간 조건을 사용할 수 있다. 앱은 지갑 내부 규칙을 모두 알지 않아도 되지만, 서명한 내용과 실패 처리, 검사 시점을 책임져야 한다.

Safe 사례에서 중요한 것은 공유 보조 프로그램의 주소보다 각 Safe 계정의 현재 소유자와 승인 규칙이다. 한 줄로 정리하면 ERC-1271은 “컨트랙트 지갑도 자신의 규칙에 따라 유효한 서명이라고 대답할 수 있게 만든 표준”이다.
