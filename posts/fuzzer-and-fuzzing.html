MISSION #19

목표는 퍼징의 개념과 종류를 이해하고 여러 퍼저의 차이를 설명하는 것이다. 아래 내용은 AFL++, LLVM, Google Project Zero, OSS-Fuzz와 각 프로젝트의 공식 문서를 기준으로 정리했다.

“퍼징은 프로그램에 무작위 값을 넣어 보는 테스트”라는 설명은 반만 맞다. 현대 퍼저는 단순히 난수를 던지는 데서 끝나지 않는다. 이전 입력을 변형하고, 그 입력이 새로운 코드 경로를 열었는지 관찰하고, 가치 있는 입력만 코퍼스에 남긴 뒤 다시 변형한다. 즉, 자동 생성·실행·관찰·학습을 매우 빠르게 반복하는 탐색 과정에 가깝다.

퍼징이란 무엇인가

퍼징(fuzzing 또는 fuzz testing)은 정상·비정상 입력을 자동으로 생성하거나 변형해 대상 프로그램에 반복적으로 전달하고, 충돌·멈춤·메모리 오류·예외·검증 실패 같은 비정상 동작을 찾는 테스트 기법이다. 사람이 예상한 예제만 확인하는 단위 테스트와 달리, 개발자가 떠올리지 못한 입력 공간을 넓고 지속적으로 탐색하는 데 강점이 있다.

다만 “크래시가 없었다”는 사실이 “취약점이 없다”는 뜻은 아니다. 퍼저는 준비한 하네스와 오라클이 관찰할 수 있는 문제만 찾는다. 메모리 손상을 즉시 드러내는 AddressSanitizer, 정의되지 않은 동작을 잡는 UndefinedBehaviorSanitizer처럼 실패를 보이게 만드는 장치를 함께 쓰는 이유다.

ONE-LINE MODEL

퍼징 = 입력 탐색기 + 대상 실행기 + 피드백 + 실패 판정기 + 재현 가능한 증거.

현대적인 퍼저는 어떻게 움직이는가

COVERAGE-GUIDED LOOPFUZZ
초기 시드 코퍼스
      │
      ▼
입력 선택 ─→ 변형(mutation) ─→ 하네스로 대상 실행
  ▲                                  │
  │                                  ▼
  └──── 새 경로면 코퍼스에 보존 ← 커버리지 피드백
                                      │
                 크래시·행·sanitizer 오류면 별도 저장
                                      │
                                      ▼
                        중복 제거 → 최소화 → 재현 → 수정
  1. 대상을 좁힌다. 파일 파서, 디코더, 프로토콜 메시지 처리 함수처럼 입력 경계가 뚜렷한 코드를 고른다.
  2. 하네스를 만든다. 바이트 배열을 실제 API 호출로 연결하고, 한 입력의 실행이 빠르고 결정적이도록 상태를 정리한다.
  3. 계측한다. 컴파일러 또는 동적 바이너리 계측으로 어떤 분기와 에지를 실행했는지 관찰한다.
  4. 시드를 준비한다. 작고 다양한 정상·비정상 샘플을 넣고, 같은 커버리지만 만드는 중복 입력은 줄인다.
  5. 반복한다. 퍼저가 입력을 변형해 새 경로를 여는 샘플을 보존하고 다시 변형한다.
  6. 트리아지한다. 발견 입력을 최소화하고 중복을 제거한 뒤, 정확한 빌드와 환경에서 재현한다.
  7. 회귀 테스트로 남긴다. 수정 후에도 크래시 입력을 테스트에 포함해 같은 버그가 돌아오지 않게 한다.

퍼징의 종류 — 하나의 축으로 나누면 헷갈린다

블랙박스·그레이박스·화이트박스, 변이 기반·생성 기반 같은 용어는 서로 대체 관계가 아니다. 하나는 내부 정보를 얼마나 쓰는지, 다른 하나는 입력을 어떻게 만드는지 설명한다. 따라서 퍼저를 고를 때는 여러 축을 함께 봐야 한다.

분류 축종류뜻장단점
내부 정보블랙박스입출력과 충돌처럼 외부 현상만 본다.적용은 쉽지만 깊은 경로를 찾기 어렵다.
내부 정보그레이박스커버리지 같은 가벼운 실행 피드백을 사용한다.속도와 탐색 능력의 균형이 좋아 가장 널리 쓰인다.
내부 정보화이트박스기호 실행·제약 해결 등 프로그램 의미를 깊게 분석한다.어려운 조건을 풀 수 있지만 계산 비용이 크다.
입력 생성변이 기반기존 시드의 비트·바이트·블록을 바꾸거나 결합한다.설정은 쉽지만 강한 문법 검증 앞에서 막힐 수 있다.
입력 생성생성 기반문법·모델·AST에 따라 처음부터 유효한 입력을 만든다.깊은 파싱 단계에 도달하지만 모델 작성 비용이 든다.
입력 생성구조 인식·혼합구조를 보존한 변이와 일반 변이를 함께 사용한다.유효성과 예상 밖 입력의 균형을 잡는다.
실행 모델프로세스 밖각 입력을 새 프로세스·forkserver·별도 대상에 전달한다.격리는 강하지만 시작 비용이 생긴다.
실행 모델인프로세스퍼저와 대상 라이브러리를 한 프로세스에서 반복 호출한다.매우 빠르지만 전역 상태 초기화와 결정성이 중요하다.
대상 형태파일·API·프로토콜·상태 기반단일 입력인지, 요청 순서와 세션 상태까지 다루는지 구분한다.네트워크 프로토콜은 메시지뿐 아니라 상태 전이도 탐색해야 한다.
TERMINOLOGY TRAP

“소스 없는 바이너리”와 “피드백 없는 블랙박스”는 같지 않다. Jackalope처럼 소스가 없어도 TinyInst로 바이너리를 동적 계측해 커버리지를 얻는 퍼저가 있다. 소스 접근성, 계측 방식, 피드백 수준은 따로 확인해야 한다.

퍼징을 이해하기 위한 핵심 용어

코퍼스와 시드

코퍼스는 퍼저가 재료로 사용하는 입력 집합이고, 시드는 시작할 때 넣는 초기 입력이다. 좋은 코퍼스는 파일 수가 많은 것이 아니라 작은 입력으로 서로 다른 동작을 많이 일으키는 집합이다. 새 커버리지를 만들지 않는 중복 샘플은 실행 시간만 차지한다.

하네스

하네스는 퍼저의 바이트 입력을 테스트 대상 API에 연결하는 얇은 코드다. 같은 퍼저라도 하네스가 느리거나 너무 넓으면 초당 실행 수가 줄고, 입력이 중요한 로직까지 도달하지 못한다. libFuzzer 계열의 가장 단순한 형태는 다음과 같다.

MINIMAL HARNESSC++
#include <cstddef>
#include <cstdint>

extern "C" int LLVMFuzzerTestOneInput(
    const uint8_t* data, size_t size) {
  if (size > 1'000'000) return 0;
  parse_untrusted_document(data, size);
  return 0;
}

계측과 커버리지

계측은 실행 중 어떤 코드가 지나갔는지 알기 위한 관찰 장치를 넣는 일이다. 소스 빌드 시 컴파일러가 넣을 수도 있고, QEMU·Frida·TinyInst 같은 도구가 바이너리 실행 중 넣을 수도 있다. 라인 수 자체보다 새로운 에지와 분기처럼 행동이 달라졌음을 알려 주는 신호가 중요하다.

오라클과 sanitizer

오라클은 무엇을 실패로 볼지 정하는 규칙이다. 크래시와 타임아웃은 기본 오라클이고, assertion·두 구현의 결과 차이·프로토콜 불변식도 사용할 수 있다. ASan·UBSan·MSan은 조용히 지나갈 메모리 오류와 정의되지 않은 동작을 즉시 실패로 바꿔 퍼저가 저장할 수 있게 한다.

대표 퍼저 8종 비교

“어떤 퍼저가 가장 좋은가”보다 “내 대상과 제약에 어떤 퍼저가 맞는가”가 정확한 질문이다. 아래 표는 각 프로젝트의 공식 문서를 기준으로 같은 질문을 던져 정리한 것이다.

퍼저주 대상실행·피드백소스·계측 조건잘 맞는 상황주의점
AFL++C/C++·바이너리주로 프로세스 밖, 에지 커버리지, forkserver·persistent소스 계측 또는 QEMU·Frida 등 바이너리 계측범용 캠페인, 다양한 계측 백엔드와 변이 전략모드가 많아 대상에 맞는 설정과 성능 측정이 필요하다.
libFuzzerC/C++ 라이브러리인프로세스, LLVM SanitizerCoverageClang으로 대상과 하네스를 계측·링크할 수 있어야 함좁은 API와 빠른 하네스, sanitizer 결합대상 상태를 매 반복마다 깨끗이 되돌려야 한다.
Jackalope폐쇄형 바이너리TinyInst 기반 커버리지, 분산 실행소스 불필요, TinyInst 동적 계측Windows·macOS 등 소스 없는 바이너리와 사용자 정의 전달 방식기본 변이는 단순해 대상별 mutator 작성이 중요하다.
Honggfuzz네이티브 프로그램SW/HW 커버리지, 멀티프로세스·persistent컴파일러 계측 또는 지원되는 HW·바이너리 피드백간결한 범용 실행과 강한 크래시 감시계측·플랫폼별 기능 차이를 확인해야 한다.
LibAFL맞춤형 퍼저구성 요소를 조립하는 Rust 프레임워크대상에 따라 SanitizerCoverage·Frida·QEMU·TinyInst 선택임베디드·하이퍼바이저·특수 입력 등 연구와 커스텀 환경완성형 CLI보다 설계·구현 비용이 크다.
JazzerJava·Kotlin·JVM인프로세스, 커버리지 기반, libFuzzer 계열대상 JVM 바이트코드와 fuzz test 필요JUnit과 함께 JVM 애플리케이션을 퍼징할 때네이티브 메모리 버그보다 JVM용 bug detector와 예외 설계가 핵심이다.
AtherisPython·CPython 확장Python 바이트코드 계측, libFuzzer 기반가져올 수 있는 Python 모듈, 네이티브 확장은 별도 계측파서·직렬화 코드와 네이티브 확장을 함께 볼 때계측되지 않은 Python 코드는 커버리지 피드백을 주지 않는다.
FuzzilliJavaScript 엔진FuzzIL 프로그램 변이, 커버리지 기반대상 엔진의 coverage·REPRL 패치와 빌드 필요동적 언어 엔진의 구조 있는 프로그램 생성일반 웹앱용 퍼저가 아니며 대상 엔진 통합 비용이 크다.

각 퍼저의 차이를 조금 더 자세히

AFL++ — 범용성과 선택지가 강점

AFL++는 AFL에서 출발한 커버리지 기반 진화형 퍼저다. 소스가 있으면 컴파일러 래퍼로 계측하고, 바이너리만 있으면 QEMU·Frida·Unicorn 같은 모드를 선택할 수 있다. forkserver는 매 입력마다 프로그램을 처음부터 실행하는 비용을 줄이고, persistent mode는 한 프로세스 안에서 여러 입력을 처리해 더 빠르게 만든다. 다양한 power schedule, dictionary, custom mutator가 있어 일반적인 네이티브 대상에서 첫 선택지로 삼기 좋다.

libFuzzer — 함수 단위로 매우 빠르게

libFuzzer는 대상 라이브러리와 같은 프로세스에 링크되는 LLVM의 커버리지 기반 엔진이다. LLVMFuzzerTestOneInput 함수를 반복 호출하므로 프로세스 시작 비용이 거의 없고 ASan·UBSan과 결합하기 쉽다. 반면 한 입력이 남긴 전역 상태, 스레드, 캐시가 다음 입력에 영향을 주면 재현성이 떨어진다. LLVM 문서에 따르면 현재 중요한 버그 수정은 계속되지만 원 저자들의 적극적인 기능 개발은 Centipede로 이동했다.

Jackalope — 소스 없는 데스크톱 바이너리에 강한 도구

Google Project Zero의 Jackalope는 사용자 정의가 가능한 분산형 커버리지 기반 퍼저다. 기본적으로 TinyInst로 바이너리를 계측하며 Windows, macOS, Linux, Android의 블랙박스 바이너리를 지원한다. 파일과 공유 메모리 입력 전달, 문법 기반 mutation, 단일·다중 머신 병렬 실행을 제공한다. 공식 문서가 밝히듯 고급 mutation 전략이 기본 제공되는 것은 아니므로, 특수 형식에서는 custom mutator가 성능을 좌우한다.

Honggfuzz — 실행과 크래시 감시에 집중한 범용 퍼저

Honggfuzz는 소프트웨어·하드웨어 커버리지를 이용하는 피드백 기반 퍼저다. 멀티프로세스·멀티스레드와 persistent mode를 지원하고, 낮은 수준의 운영체제 인터페이스로 숨은 충돌을 감시한다. AFL++와 역할이 겹치지만 비교적 직접적인 실행 흐름과 강한 프로세스 모니터링을 선호할 때 검토할 수 있다.

LibAFL — 퍼저가 아니라 퍼저를 만드는 부품 상자

LibAFL은 Rust로 작성된 모듈형 퍼징 프레임워크다. 입력 표현, 스케줄러, 실행기, 관찰자, 피드백을 교체할 수 있고 SanitizerCoverage·Frida·QEMU·TinyInst 백엔드를 제공한다. Windows, macOS, iOS, Linux, Android뿐 아니라 no_std 환경까지 겨냥한다. 기존 퍼저의 실행 모델로는 맞지 않는 펌웨어·하이퍼바이저·임베디드 대상을 다룰 때 강력하지만, 그만큼 퍼징 시스템 자체를 설계해야 한다.

언어·도메인 특화 퍼저 — 런타임의 의미를 활용한다

Jazzer는 JVM 바이트코드와 JUnit 생태계에, Atheris는 Python 바이트코드와 CPython 확장에 맞춰져 있다. Fuzzilli는 단순 바이트가 아니라 자체 중간 표현인 FuzzIL 프로그램을 변형해 JavaScript 엔진이 이해할 수 있는 유효한 코드를 만든다. 범용 바이트 변이만으로 통과하기 어려운 언어 문법과 런타임 상태를 아는 것이 특화 퍼저의 장점이다.

상황별 선택 기준

  • C/C++ 소스와 작은 API가 있다: libFuzzer로 빠른 인프로세스 하네스를 만들고 sanitizer를 붙인다.
  • 전체 실행 파일과 파일 입력을 다룬다: AFL++ 또는 Honggfuzz로 시작해 실행 속도와 커버리지를 비교한다.
  • Windows·macOS의 소스 없는 바이너리다: Jackalope와 TinyInst 조합을 우선 검토한다.
  • Python 또는 JVM 프로젝트다: Atheris 또는 Jazzer로 언어 런타임의 커버리지를 직접 사용한다.
  • JavaScript 엔진 자체가 대상이다: 구조 있는 프로그램을 생성하는 Fuzzilli가 더 알맞다.
  • 임베디드·펌웨어·특수 피드백이 필요하다: LibAFL로 입력·실행기·관찰자를 조합한다.
  • 복잡한 파일 형식이다: dictionary, grammar, structure-aware custom mutator를 추가한다.
  • 상태 기반 네트워크 프로토콜이다: 단일 패킷뿐 아니라 메시지 순서와 상태 전이를 모델링하는 퍼저가 필요하다.

실제로는 하나만 고집할 필요가 없다. 같은 하네스를 AFL++와 libFuzzer에서 돌려 결과를 교환하거나, 서로 다른 퍼저의 코퍼스를 주기적으로 합치는 방식은 탐색 편향을 줄인다. 중요한 지표도 단순한 초당 실행 수 하나가 아니다. 시간당 새 에지, 안정성, 중복 제거 후 고유 충돌, 재현율을 함께 봐야 한다.

퍼징이 놓치는 것과 안전한 운영

도달하지 못하면 찾지 못한다

체크섬, 암호, 압축, 긴 상태 전이처럼 입력과 분기 조건 사이의 관계가 복잡하면 무작위 변이만으로 통과하기 어렵다. 좋은 시드, dictionary, 비교 로깅, 문법 기반 변이, concolic execution 같은 보조 기법이 필요한 이유다.

오라클이 없으면 논리 버그는 조용히 지나간다

권한이 잘못 부여되거나 계산 결과가 미세하게 틀려도 프로그램이 죽지 않을 수 있다. “절대 음수가 될 수 없다” 같은 불변식을 assertion으로 만들거나, 두 구현의 결과를 비교하는 differential testing을 사용해야 이런 버그를 포착할 수 있다.

퍼징 자체도 격리해야 한다

퍼저는 의도적으로 비정상 동작을 유발하며 CPU·메모리·디스크를 오래 사용한다. AFL++ 문서도 데이터 손실을 감수할 수 없는 시스템에서 실행하지 말라고 경고한다. 대상이 파일 삭제, 네트워크 요청, 장치 제어 같은 부작용을 일으킬 수 있다면 VM·컨테이너·최소 권한 계정에서 외부 네트워크와 실제 자원을 차단해야 한다. 내가 소유하거나 테스트 권한을 받은 대상에서만 실행하는 것도 기본 조건이다.

범위를 허가받았는가 → 하네스가 빠르고 결정적인가 → sanitizer와 오라클이 있는가 → 코퍼스가 작고 다양한가 → 실행 환경이 격리됐는가 → 크래시를 최소화·중복 제거·재현했는가 → 수정 입력을 회귀 테스트로 남겼는가.

정리 — 좋은 퍼저보다 좋은 퍼징 캠페인

이번 학습을 통해 퍼징은 운에 맡기는 무작위 테스트가 아니라 피드백으로 입력 공간을 탐색하는 자동화된 실험이라는 점을 이해했다. AFL++와 libFuzzer의 핵심 차이는 단순한 성능 순위가 아니라 실행 모델과 하네스의 경계에 있고, Jackalope의 강점은 소스 없는 바이너리에서도 동적 계측으로 커버리지를 얻는 데 있다. LibAFL은 완제품이 아닌 조립식 프레임워크이며 Jazzer·Atheris·Fuzzilli는 각 언어와 런타임의 구조를 활용한다.

결국 발견 성과를 좌우하는 것은 도구 이름 하나가 아니다. 적절히 좁힌 대상, 빠르고 결정적인 하네스, 의미 있는 시드, 커버리지 피드백, 강한 오라클, sanitizer, 그리고 발견 이후의 재현과 회귀 테스트가 한 흐름으로 이어져야 한다. 다음 실습에서는 작은 오픈소스 파서를 대상으로 같은 하네스를 libFuzzer와 AFL++에서 실행해 실행 속도·커버리지·코퍼스 증가를 직접 비교해 볼 계획이다.
